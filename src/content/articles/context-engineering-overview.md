[지난 글](/articles/tool-schema-design)에서 도구 스키마가 매 요청마다 컨텍스트에 실린다는 얘기를 했다. 스키마만 그런 게 아니다. 시스템 프롬프트, 대화 이력, 검색해 온 문서, 도구가 돌려준 결과가 전부 같은 창을 나눠 쓴다. 그런데 이것들을 한 덩어리 "프롬프트"로 보면 문제가 생겼을 때 어디를 줄여야 할지가 안 보인다. 항목마다 자라는 속도도, 줄이는 방법도 다르기 때문이다.

## 다섯 항목을 성질로 나눈다

컨텍스트를 예산표처럼 보면 관리 방법이 갈린다.

![컨텍스트 창의 항목별 예산 배분](/assets/posts/context-engineering-overview-budget.svg)

| 항목 | 성질 | 자라는 속도 | 주된 관리법 |
| --- | --- | --- | --- |
| 시스템 프롬프트 | 고정 | 안 자란다 | 캐시, 주기적 감량 |
| 도구 스키마 | 고정 | 도구 추가 시에만 | 캐시, 노출 범위 조절 |
| 대화 이력 | 누적 | 턴마다 | 잘라내기, 요약 |
| 도구 결과 | 누적 | 호출마다 | 반환 필드 축소, 오래된 것 축약 |
| 검색 문서 | 선택 | 요청마다 새로 | 개수·순서 조정 |
| 출력 몫 | 예약 | — | 먼저 떼어 둔다 |

이 표를 만들어 두고 실제 요청 하나의 토큰을 항목별로 세어 보면, 대개 예상과 다른 곳이 부풀어 있다. 흔한 범인은 도구 결과다. 조회 API 응답을 그대로 넘기는 코드가 몇 군데 있으면 대화 열 턴 만에 이력의 절반을 차지한다.

## 고정 항목 — 캐시가 붙는 자리다

시스템 프롬프트와 도구 스키마는 매 요청 똑같이 들어간다. 그래서 프리픽스 캐싱의 효과가 가장 큰 자리다. 캐시가 듣게 하려면 규칙이 하나다 — **바뀌지 않는 것을 앞에, 바뀌는 것을 뒤에** 둔다.

이 원칙을 깨는 흔한 패턴이 시스템 프롬프트에 현재 시각이나 사용자 이름을 넣는 것이다. 한 줄 때문에 그 뒤의 모든 캐시가 무효화된다. 시각이 정말 필요하다면 시스템 프롬프트가 아니라 **대화의 마지막 사용자 메시지 쪽**에 붙인다.

```text
[캐시 되는 구간]              [캐시 안 되는 구간]
시스템 프롬프트 → 도구 스키마 → 대화 이력 → 검색 문서 → 이번 질문
```

고정 항목은 캐시가 듣더라도 무한정 늘려도 되는 것은 아니다. 캐시는 비용과 지연을 줄여 주지만 모델이 읽어야 할 양은 그대로다. 지시가 서른 줄을 넘어가면 서로 부딪히는 문장이 생기고, 그때부터는 길이가 품질을 깎는다. 시스템 프롬프트는 주기적으로 줄여야 하는 자산이다.

## 누적 항목 — 방치하면 여기가 먼저 넘친다

대화 이력과 도구 결과는 아무것도 안 하면 계속 자란다. 다루는 방법은 셋이고, 셋 다 쓰는 것이 보통이다.

**잘라내기.** 오래된 턴부터 버린다. 가장 단순하고 가장 안전하다. 다만 시스템 메시지와 최초의 과제 서술은 남겨야 한다 — 이게 잘려 나가면 에이전트가 자기가 뭘 하던 중인지를 잃는다.

**요약.** 오래된 구간을 모델에게 요약시켜 한 덩어리로 대체한다. 정보를 더 오래 들고 갈 수 있지만, 요약 자체가 모델 호출이라 비용과 지연이 붙고 요약 과정에서 사실이 뭉개질 수 있다. 요약할 때 **결정된 사항과 사용자가 명시한 제약**을 원문 그대로 보존하도록 지시하면 손실이 줄어든다.

**축약.** 도구 결과 전용 기법이다. 최근 두세 개는 전문을 두고, 그보다 오래된 것은 "이 조회는 3건을 반환했다" 수준으로 줄인다. 결과 전문이 필요하면 다시 부르면 되므로 손실이 적다.

```python
def trim_history(messages, budget_tokens):
    head = messages[:1]                      # 시스템 메시지는 항상 남긴다
    tail = messages[1:]

    while count_tokens(head + tail) > budget_tokens and len(tail) > 4:
        # 가장 오래된 도구 결과부터 축약, 그다음이 오래된 대화 턴
        idx = next((i for i, m in enumerate(tail) if m["role"] == "tool" and not m.get("shrunk")), None)
        if idx is not None:
            tail[idx] = shrink_tool_result(tail[idx])
        else:
            tail = tail[2:]                  # 사용자·어시스턴트 한 쌍씩 버린다
    return head + tail
```

턴을 버릴 때 한 쌍씩 버리는 것이 포인트다. 어시스턴트 메시지만 남기고 그에 대응하는 사용자 메시지를 지우면 대화가 앞뒤가 안 맞게 된다. 도구 호출과 그 결과도 마찬가지로 짝이다.

## 선택 항목 — 많이 넣는다고 좋아지지 않는다

검색해 온 문서는 요청마다 새로 고르는 항목이다. 여기서 가장 흔한 오해가 "창이 크니까 넉넉히 넣자"는 것이다. 실제로는 개수를 늘리면 정확도가 오르다가 어느 지점부터 떨어진다. 관련 없는 문서가 늘면 모델이 근거를 잘못 고를 확률도 같이 오르기 때문이다.

몇 개가 적당한지는 데이터마다 다르지만, 정하는 방법은 같다. 검색 개수를 3·5·8·12로 바꿔 가며 평가셋을 돌려 정확도가 꺾이는 지점을 찾는다. 그 값이 그 시스템의 상한이다. 대개 생각보다 작다.

순서도 개수만큼 중요하다. 여러 문서를 넣을 때 **가장 관련 높은 것을 앞이나 뒤에** 두고 중간을 채우는 배치가 안전하다. 이유는 다음 글에서 자세히 본다.

## 예약 항목 — 출력 몫을 먼저 뗀다

컨텍스트 창은 입력과 출력이 나눠 쓰는 공간이다. 입력을 창 끝까지 채우면 답이 중간에 잘린다. 그래서 예산은 이 순서로 짠다.

$$B_{\text{입력}} = C_{\max} - T_{\text{출력}} - S$$

$C_{\max}$는 모델의 창 크기, $T_{\text{출력}}$은 이 작업에서 필요한 최대 출력 길이, $S$는 안전 여유다. 토큰 계산이 항상 정확하지는 않으므로 $S$를 창의 5% 정도 두는 편이 안전하다. 특히 한국어는 토크나이저에 따라 추정치와 실제가 꽤 벌어진다.

남은 $B_{\text{입력}}$을 항목에 배분하면 이런 모양이 된다.

```python
def build_context(model_window, max_output):
    budget = model_window - max_output - int(model_window * 0.05)

    fixed = count_tokens(SYSTEM_PROMPT) + count_tokens(TOOL_SCHEMAS)
    budget -= fixed                                   # 고정분을 먼저 뺀다

    docs_budget = int(budget * 0.4)                   # 검색 문서 몫
    history_budget = budget - docs_budget             # 나머지가 이력 몫
    return docs_budget, history_budget
```

비율은 작업 성격이 정한다. 문서 질의응답이면 검색 문서 쪽이 크고, 긴 협업 대화라면 이력 쪽이 크다. 중요한 것은 비율의 정확한 값이 아니라 **어딘가에 명시적으로 적혀 있다는 사실**이다. 적어 두지 않으면 자라는 항목이 나머지를 조용히 밀어낸다.

## 무엇부터 재는가

컨텍스트 문제는 대개 "토큰이 모자라다"로 보고되지만, 실제로는 어느 항목이 자기 몫을 넘긴 것이다. 그래서 첫 작업은 줄이는 게 아니라 **세는 것**이다. 요청 하나를 골라 항목별 토큰 수를 로그로 남겨 보면 어디를 손대야 할지가 바로 나온다.

세어 보면 보통 이 순서로 이득이 크다. 도구 결과의 불필요한 필드를 쳐낸다. 시스템 프롬프트에서 중복되는 지시를 합친다. 검색 문서 개수를 평가로 정한다. 그다음에야 이력 요약 같은 정교한 기법이 값을 한다.
