시험 가이드 v1.1의 Task 2.3은 생성형 AI 애플리케이션을 만들 때 쓰는 AWS 인프라와 기술을 묻습니다. 목표 문장에 서비스 이름이 여럿 적혀 있고, 이어서 그 서비스들을 쓰는 이점과 비용의 트레이드오프를 따로 적었습니다. 이름이 많아 외울 목록처럼 보이지만, 서비스마다 **누가 무엇을 손대는가**가 다르고 그 차이로 갈립니다. 모델을 부르기만 하는가, 모델을 직접 띄우는가, 에이전트를 만드는가, 완성된 도구를 쓰는가의 넷입니다.

## Amazon Bedrock

### 하나의 API

**Amazon Bedrock**은 여러 회사의 파운데이션 모델을 하나의 API로 부르게 해 주는 완전관리형 서비스입니다. 서버를 띄우거나 모델 가중치를 내려받을 필요 없이, 모델 ID만 바꿔 다른 모델을 부릅니다. 이렇게 인프라를 신경 쓰지 않고 호출한 만큼만 내는 방식을 **서버리스**라 부릅니다. 입력과 출력의 토큰 수는 응답에 함께 돌아오므로 비용을 그 자리에서 셀 수 있습니다.

```python
import boto3

client = boto3.client("bedrock-runtime", region_name="us-east-1")
resp = client.converse(
    modelId="amazon.nova-lite-v1:0",  # 리전에 따라 추론 프로파일 ID를 써야 할 수 있다
    messages=[{"role": "user", "content": [{"text": "반품 규정을 세 줄로 요약해 줘"}]}],
)
usage = resp["usage"]
print(usage["inputTokens"], usage["outputTokens"])
```

Bedrock 안에는 모델 호출 말고도 앞 편들에서 본 기능이 함께 들어 있습니다. 문서를 검색해 답에 붙이는 Knowledge Bases, 유해한 입출력을 거르는 Guardrails, 프롬프트를 버전으로 관리하는 Prompt Management가 그것입니다.

### Amazon Nova

**Amazon Nova**는 AWS가 직접 만든 파운데이션 모델 계열이고 Bedrock에서 부릅니다. 텍스트와 이미지를 읽고 글을 쓰는 이해 모델이 크기별로 있고, 이미지를 그리는 Nova Canvas, 영상을 만드는 Nova Reel, 음성으로 실시간 대화하는 Nova Sonic처럼 만드는 것이 다른 모델도 있습니다. Bedrock이 모델을 고르는 시장이라면, Nova는 그 시장에 AWS가 직접 내놓은 상품입니다.

## SageMaker AI와 JumpStart

### SageMaker AI

**Amazon SageMaker AI**는 ML 모델을 직접 만들고 학습시키고 배포하는 전 과정을 다루는 플랫폼입니다. 데이터 준비, 학습 작업, 엔드포인트 배포, 모니터링까지 들어 있고, 인스턴스 종류와 개수를 사용자가 정합니다. 그만큼 손이 많이 가지만 통제할 수 있는 범위도 넓습니다.

### SageMaker JumpStart

**SageMaker JumpStart**는 SageMaker AI 안에 있는 모델 허브로, 공개 모델과 상용 모델을 골라 몇 번의 클릭이나 몇 줄의 코드로 내 계정의 엔드포인트에 띄우고 파인튜닝할 수 있게 해 줍니다. Bedrock과 가장 헷갈리는 자리인데, 갈리는 선은 **모델이 어디에서 도는가**입니다. Bedrock은 AWS가 운영하는 곳에서 돌고 우리는 호출만 하지만, JumpStart로 띄운 모델은 우리가 고른 인스턴스 위에서 돌고 인스턴스가 켜져 있는 시간만큼 돈이 듭니다.

| 기준 | Amazon Bedrock | SageMaker JumpStart |
| --- | --- | --- |
| 인프라 관리 | 없음(서버리스) | 인스턴스를 고르고 운영 |
| 과금 단위 | 주로 토큰 | 주로 인스턴스 사용 시간 |
| 통제 범위 | 모델 ID와 파라미터 | 인스턴스·컨테이너·학습 설정까지 |
| 맞는 자리 | 빠르게 여러 모델을 써 봄 | 모델과 환경을 직접 다뤄야 함 |

## 에이전트를 만드는 도구

### Bedrock AgentCore

**Amazon Bedrock AgentCore**는 에이전트를 실제 서비스로 운영하는 데 필요한 부품을 관리형으로 모은 것입니다. 에이전트 코드를 띄우는 Runtime, 단기·장기 기억을 맡는 Memory, 기존 API를 에이전트가 부를 도구로 바꾸는 Gateway, 사용자와 에이전트의 권한을 다루는 Identity, 실행을 추적하는 Observability가 들어 있습니다. 어떤 프레임워크로 짠 에이전트든 올릴 수 있다는 점이 특징입니다.

### Strands Agents

**Strands Agents**는 AWS가 공개한 오픈소스 SDK로, 에이전트를 코드 몇 줄로 짜게 해 줍니다. 모델·시스템 프롬프트·도구 목록만 주면 다음 할 일을 모델이 정하는 되풀이를 SDK가 돌립니다. 짜는 것은 Strands, 운영하는 자리는 AgentCore라는 관계로 둘이 이어집니다.

### Kiro

**Kiro**는 AI 에이전트가 들어간 개발 환경(IDE)입니다. 요구사항을 적으면 에이전트가 그것을 명세와 설계, 작업 목록으로 나눈 뒤 코드를 쓰는 명세 중심 개발을 내세웁니다. 앞의 둘이 에이전트를 만드는 도구라면, Kiro는 개발자가 에이전트의 도움을 받아 소프트웨어를 만드는 도구입니다.

## 완성된 업무 서비스

### Amazon Quick

**Amazon Quick**은 업무 사용자가 코드 없이 쓰는 에이전트형 작업 공간입니다. 사내 문서·데이터베이스·업무 앱에 연결해 자연어로 묻고, 대시보드를 만들고, 조사 보고서를 받고, 반복 업무를 자동 흐름으로 만듭니다. 쓰는 사람이 개발자가 아니라 현업이라는 점이 앞 절의 도구들과 갈리는 선입니다.

### AWS Transform

**AWS Transform**은 오래된 시스템을 옮기고 현대화하는 일을 에이전트가 맡는 서비스입니다. 메인프레임의 COBOL 코드를 분석해 현대 언어로 바꾸거나, VMware 가상 머신을 AWS로 옮기거나, .NET Framework 애플리케이션을 리눅스에서 도는 판으로 바꾸는 일이 그 자리입니다. 문항이 「레거시 현대화」나 「마이그레이션 자동화」를 묘사하면 이 서비스입니다.

## 서비스의 이점

### 접근성과 낮은 진입 장벽

시험 가이드는 AWS 생성형 AI 서비스의 이점을 다섯 낱말로 적습니다 — 접근성, 낮은 진입 장벽, 효율, 비용 효율, 출시 속도입니다. 접근성은 여러 회사의 모델을 한 계정과 한 API로 쓸 수 있다는 뜻이고, 낮은 진입 장벽은 GPU를 사거나 모델을 학습시킬 전문 인력이 없어도 시작할 수 있다는 뜻입니다.

### 효율과 비용 효율

효율은 인프라 운영을 AWS가 맡아 팀이 업무 로직에 집중한다는 뜻이고, 비용 효율은 쓴 만큼만 내므로 수요가 적거나 들쭉날쭉한 초기에 장비를 미리 사 두지 않아도 된다는 뜻입니다. 출시 속도는 이 넷이 합쳐진 결과로, 시제품을 며칠 안에 만들어 실제 사용자에게 보여 줄 수 있다는 점입니다.

## 비용 구조

### 토큰 기반 과금

Bedrock의 기본 과금은 **온디맨드**, 곧 호출할 때마다 처리한 토큰 수만큼 내는 방식입니다. 입력 토큰과 출력 토큰의 단가가 따로 있고 대개 출력 쪽이 비쌉니다. 가상의 단가로 입력 100만 토큰당 0.5달러, 출력 100만 토큰당 2달러인 모델이 있다고 합시다. 요청 한 번에 입력 2,000토큰·출력 500토큰이 들고 하루 1만 번 부르면, 입력은 $$2000 \times 10000 = 2 \times 10^{7}$$ 토큰이라 10달러, 출력은 $$500 \times 10000 = 5 \times 10^{6}$$ 토큰이라 10달러로 하루 20달러입니다. 출력 토큰은 입력의 4분의 1인데 비용은 같다는 점이 단가 차이를 보여 줍니다.

### 프로비저닝된 처리량

**프로비저닝된 처리량**은 모델 처리 용량을 정해진 단위로 미리 사서 시간당 고정 요금을 내는 방식입니다. 호출이 적든 많든 같은 돈이 나가는 대신, 정해 둔 만큼의 처리량이 늘 보장됩니다. 그래서 둘의 갈림은 사용량입니다 — 요청이 적거나 들쭉날쭉하면 온디맨드가 싸고, 크고 꾸준한 사용량에 일정한 처리 속도가 필요하면 프로비저닝된 처리량이 맞습니다. 앞의 하루 20달러짜리 서비스에 시간당 수십 달러의 용량을 사는 것은 낭비입니다.

### 커스텀 모델과 리전

파인튜닝한 **커스텀 모델**은 비용이 두 겹 더 붙습니다. 학습할 때 처리한 토큰만큼의 학습 비용과, 만들어 둔 모델을 보관하는 월 비용입니다. 모델에 따라서는 그 모델을 부르려면 프로비저닝된 처리량을 따로 사야 합니다. 프롬프트와 검색으로 풀 수 있는 문제를 파인튜닝으로 풀면 이 비용이 그대로 얹히는 셈입니다.

마지막 트레이드오프는 리전 커버리지입니다. 모든 모델이 모든 리전에 있지는 않아서, 쓰려는 모델이 데이터를 둬야 하는 리전에 없을 수 있습니다. 여러 리전에 요청을 나눠 보내는 교차 리전 추론으로 처리량을 늘릴 수 있지만, 데이터가 다른 리전을 지나도 되는지는 앞 편의 컴플라이언스 요건으로 먼저 따져야 합니다.

## 연습 문제

1. 스타트업이 GPU 서버 없이 여러 회사의 텍스트 모델을 같은 코드로 바꿔 가며 시험해 보려 합니다. 가장 알맞은 서비스는?\
   ① Amazon Bedrock\
   ② Amazon EC2에 모델을 직접 설치\
   ③ AWS Transform\
   ④ Amazon Quick

   답. ①. 모델 ID만 바꿔 여러 모델을 서버리스로 부르는 것이 Bedrock입니다.
2. 입력 100만 토큰당 1달러, 출력 100만 토큰당 4달러인 모델을 요청 한 번에 입력 3,000토큰·출력 1,000토큰으로 하루 5,000번 부릅니다. 하루 비용은?\
   ① 15달러\
   ② 20달러\
   ③ 35달러\
   ④ 60달러

   답. ③. 입력은 $$3000 \times 5000 = 1.5 \times 10^{7}$$ 토큰이라 15달러, 출력은 $$1000 \times 5000 = 5 \times 10^{6}$$ 토큰이라 20달러, 합해 35달러입니다.
3. 설명과 서비스를 짝지으시오.\
   (가) 메인프레임 COBOL 코드를 분석해 현대 언어로 바꾼다\
   (나) 현업 사용자가 사내 데이터에 자연어로 묻고 대시보드를 만든다\
   (다) 요구사항을 명세·설계·작업 목록으로 나눈 뒤 코드를 쓰는 개발 환경\
   (라) 에이전트를 짜는 오픈소스 SDK\
   ⓐ Kiro ⓑ Strands Agents ⓒ AWS Transform ⓓ Amazon Quick

   답. (가)-ⓒ, (나)-ⓓ, (다)-ⓐ, (라)-ⓑ.
4. Amazon Bedrock AgentCore에 들어 있는 부품으로 옳은 것을 **둘** 고르시오.\
   ① 단기·장기 기억을 관리하는 Memory\
   ② 이미지를 그리는 Canvas\
   ③ 기존 API를 에이전트가 부를 도구로 바꾸는 Gateway\
   ④ 메인프레임 코드를 바꾸는 변환기\
   ⑤ 대시보드를 그리는 시각화 도구

   답. ①과 ③. ②는 Amazon Nova의 이미지 생성 모델이고, ④는 AWS Transform, ⑤는 Amazon Quick의 몫입니다.
5. 하루 24시간 내내 대량의 요청이 꾸준히 들어오고, 응답 처리량이 늘 일정해야 하는 서비스입니다. 알맞은 과금 방식은?\
   ① 온디맨드 토큰 과금\
   ② 프로비저닝된 처리량\
   ③ 무료 체험 한도\
   ④ 요청마다 모델을 새로 파인튜닝

   답. ②. 크고 꾸준한 사용량에 보장된 처리량이 필요하면 용량을 미리 사는 쪽이 맞습니다.
6. 공개 모델을 내 계정의 인스턴스에 띄우고, 인스턴스 종류와 컨테이너 설정을 직접 정하려 합니다. 알맞은 것은?\
   ① Amazon Bedrock 온디맨드\
   ② SageMaker JumpStart\
   ③ Amazon Quick\
   ④ Kiro

   답. ②. 모델이 내가 고른 인스턴스 위에서 도는 것이 JumpStart이고, 그만큼 인스턴스 시간에 비용이 듭니다.
7. 커스텀 모델을 만들 때 온디맨드 기본 모델 호출에는 없던 비용으로 옳지 않은 것은?\
   ① 학습할 때 처리한 토큰에 대한 비용\
   ② 만든 모델을 보관하는 월 비용\
   ③ 모델에 따라 필요한 프로비저닝된 처리량\
   ④ 기본 모델의 사전학습 비용 전액

   답. ④. 사전학습은 모델 제공사가 이미 마친 것이고, 커스텀 모델은 그 위에 파인튜닝 비용과 보관 비용을 더합니다.

일곱 문항 가운데 서비스를 고르는 다섯은 누가 무엇을 손대는가로 가르면 풀립니다. 계산 문항은 입력과 출력을 따로 곱한 뒤 더한다는 순서를 지키면 되고, 단가가 다르므로 토큰을 먼저 합치면 틀립니다.
