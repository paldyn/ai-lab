시험 가이드 v1.1의 도메인 3(파운데이션 모델의 활용)은 Task 3.1에서 파운데이션 모델을 쓰는 애플리케이션의 설계 고려사항을 묻고, 그 첫 목표가 사전학습 모델을 고르는 기준입니다. 두 번째 목표는 추론 파라미터가 모델의 응답에 미치는 영향입니다. 앞의 것은 **어느 모델을 부를지**, 뒤의 것은 **고른 모델을 어떻게 부를지**의 문제라 한 편에 묶었습니다. 앞 편이 모델 선택 요소를 업무 쪽에서 봤다면, 이 편은 모델 카드에 적힌 사양 쪽에서 봅니다.

## 선택 기준

### 비용과 모달리티

비용은 앞 편에서 본 대로 토큰당 단가와 호출 횟수가 정합니다. 같은 작업을 할 수 있는 모델이 둘이면 단가가 싼 쪽이 먼저지만, 품질이 모자라 다시 부르거나 사람이 고쳐야 하면 싼 모델이 오히려 비싸집니다.

**모달리티**는 모델이 다루는 데이터의 종류, 곧 텍스트·이미지·음성·영상 같은 것입니다. 입력 모달리티와 출력 모달리티를 따로 봐야 합니다. 영수증 사진을 읽어 금액을 글로 뽑으려면 이미지를 입력으로 받는 모델이어야 하고, 상품 사진을 새로 그리려면 이미지를 출력하는 모델이어야 합니다. 이 기준은 비용보다 먼저 걸러 내는 문턱입니다 — 못 읽는 데이터를 넣을 수는 없으니까요.

### 지연시간

**지연시간**은 요청을 보내고 응답을 받기까지 걸리는 시간입니다. 대화형 서비스에서는 첫 글자가 나오기까지의 시간이, 긴 보고서에서는 끝까지 다 쓰는 시간이 문제가 됩니다. 실시간 음성 상담처럼 사람이 기다리는 자리는 지연시간이 가장 앞선 기준이 되고, 밤새 도는 배치 작업에서는 거의 문제가 되지 않습니다.

### 다국어

다국어는 모델이 여러 언어를 얼마나 잘 읽고 쓰는가입니다. 모델 카드가 지원 언어를 적어 두지만, 지원한다고 적힌 언어끼리도 품질이 고르지 않습니다. 한국어 고객 상담을 할 모델이라면 한국어로 된 실제 질문 표본으로 시험해 보고 고르는 것이 안전합니다. 같은 한국어 문장이라도 모델의 토크나이저에 따라 토큰 수가 달라 비용이 달라진다는 점도 함께 봅니다.

## 모델 크기와 복잡도

### 파라미터 수

모델 크기는 대개 **파라미터** 수로 말합니다. 파라미터는 학습으로 정해져 모델 안에 저장된 숫자들이고, 추론은 그 숫자를 읽어 다음 토큰을 계산하는 일입니다. 파라미터가 많을수록 모델이 담을 수 있는 패턴이 많아 어려운 추론과 긴 지시를 더 잘 따르는 경향이 있습니다. 모델 복잡도는 크기에 더해 구조가 얼마나 복잡한가까지 덮는 말로, 여러 단계로 생각하는 추론 모델처럼 같은 크기에서도 한 번의 응답에 계산을 더 쓰는 모델이 있습니다.

### 크기의 트레이드오프

큰 모델은 정확하지만 느리고 비쌉니다. 파라미터를 읽는 계산이 그만큼 많기 때문입니다. 그래서 모델 크기는 정확도와 지연시간·비용 사이의 저울입니다.

| 작업 | 맞는 크기 | 까닭 |
| --- | --- | --- |
| 리뷰를 긍정·부정으로 분류 | 작은 모델 | 단순한 작업이고 호출이 많음 |
| 계약서 조항 사이의 모순 찾기 | 큰 모델 | 긴 문서를 정확히 따져야 함 |
| 기기 안에서 도는 음성 비서 | 작은 모델 | 메모리와 전력이 제한됨 |
| 다단계 수학 풀이 | 큰 모델이나 추론 모델 | 단계가 길고 틀리면 안 됨 |

작은 모델로 충분한 일에 큰 모델을 쓰면 정확도는 거의 안 오르고 비용만 늘어납니다. 요구를 채우는 가장 작은 모델부터 시험하는 것이 기본입니다.

## 커스터마이즈와 입출력 길이

### 커스터마이즈 가능 여부

모든 모델을 파인튜닝할 수 있는 것은 아닙니다. Bedrock에서도 모델마다 파인튜닝이나 지속 사전학습을 지원하는지가 다르게 적혀 있습니다. 사내 용어와 말투에 맞춘 모델이 꼭 필요하다는 요구가 있다면, 선택 단계에서 그 모델이 커스터마이즈를 지원하는지부터 확인해야 합니다. 나중에 알면 모델을 처음부터 다시 골라야 합니다.

### 컨텍스트 길이와 최대 출력

입력 길이의 한계는 **컨텍스트 윈도우**, 곧 모델이 한 번에 읽을 수 있는 최대 토큰 수가 정합니다. 300쪽짜리 매뉴얼을 통째로 넣고 질문하려면 그만큼 긴 컨텍스트 윈도우를 가진 모델이 필요하고, 아니면 문서를 잘라 필요한 부분만 넣어야 합니다. 출력 길이에도 따로 상한이 있어서, 긴 보고서를 한 번에 써야 하는 작업이라면 최대 출력 토큰이 넉넉한 모델을 고릅니다. 입력 상한과 출력 상한은 같은 값이 아니므로 둘을 따로 봅니다.

## 프롬프트 캐싱

### 캐시 지점

**프롬프트 캐싱**은 호출마다 똑같이 앞에 붙는 긴 부분, 예컨대 시스템 프롬프트나 참고 문서를 모델 쪽에서 한 번 처리해 저장해 두고, 다음 호출에서는 그 저장분을 다시 쓰는 기능입니다. Bedrock에서는 프롬프트 안에 캐시 지점을 표시해, 그 지점까지의 앞부분을 캐시로 둡니다. 캐시는 일정 시간 동안만 살아 있으므로, 같은 머리말로 짧은 간격을 두고 여러 번 부르는 작업에서 효과가 큽니다.

### 비용과 지연

캐시에서 읽은 토큰은 새로 처리하는 토큰보다 단가가 싸고, 모델이 그 부분을 다시 계산하지 않아 응답도 빨라집니다. 가상의 조건으로 따져 봅시다. 시스템 프롬프트가 8,000토큰, 사용자 질문이 200토큰이고 1,000번 부릅니다. 캐시를 읽는 단가를 정가의 10퍼센트로 두고, 첫 호출의 캐시 저장은 정가로 셉니다.

- 캐싱 없음: $$8200 \times 1000 = 8200000$$ 토큰 분량
- 캐싱 있음: 나머지 999번은 한 번에 $$8000 \times 0.1 + 200 = 1000$$ 토큰 분량이므로, 첫 호출 8,200을 더해 $$8200 + 999 \times 1000 = 1007200$$ 토큰 분량

입력 비용이 대략 8분의 1로 줄었습니다. 반대로 머리말이 호출마다 바뀌거나 호출 간격이 캐시 수명보다 길면 다시 쓸 것이 없어 이득이 없습니다. 캐싱은 컨텍스트의 양을 줄이는 것이 아니라 같은 양을 보내는 값을 줄인다는 점이 앞서 본 요약·선별과 갈리는 자리입니다.

## 추론 파라미터

### temperature

**추론 파라미터**는 모델을 다시 학습시키지 않고 호출할 때마다 응답의 모양을 조절하는 값입니다. 모델은 다음 토큰 후보마다 확률을 매기고 그 가운데 하나를 뽑는데, 추론 파라미터는 그 뽑는 방식을 바꿉니다.

**temperature**는 확률 분포를 얼마나 평평하게 할지 정합니다. 낮추면 가장 확률이 높은 후보 쪽으로 쏠려 답이 일정해지고, 높이면 낮은 후보도 뽑힐 기회가 늘어 답이 다양해집니다. 약관 요약이나 데이터 추출처럼 매번 같은 답이 나와야 하는 일에는 낮게, 광고 문구 아이디어처럼 여러 갈래가 필요한 일에는 높게 둡니다. 앞 편의 비결정성을 줄이는 손잡이가 이것입니다.

### top-p와 top-k

**top-k**는 확률이 높은 순서로 k개의 후보만 남기고 그 안에서 뽑게 합니다. **top-p**는 확률이 높은 순서로 더해 가다가 합이 p에 닿는 데까지의 후보만 남깁니다. 다음 토큰 후보가 「서울 0.5, 부산 0.2, 대구 0.15, 광주 0.1, 그 밖 0.05」라면, top-k가 2일 때 서울·부산만 남습니다. top-p가 0.8이면 0.5, 0.7, 0.85로 더해 가다 0.8을 넘는 대구까지, 곧 서울·부산·대구가 남습니다. top-k는 후보의 개수를, top-p는 후보 확률의 합을 자른다는 것이 둘의 차이입니다.

### 최대 토큰 수

최대 토큰 수는 응답으로 만들 토큰의 상한입니다. 비용과 지연을 묶어 두는 안전장치지만, 너무 낮으면 문장이 중간에 끊깁니다. Converse API로는 네 값을 한 자리에 넘깁니다.

```python
resp = client.converse(
    modelId="amazon.nova-lite-v1:0",
    messages=[{"role": "user", "content": [{"text": "신제품 슬로건 다섯 개"}]}],
    inferenceConfig={"temperature": 0.9, "topP": 0.9, "maxTokens": 300},
)
print(resp["stopReason"])  # 상한에 걸려 끊겼으면 max_tokens
```

`stopReason`이 `max_tokens`로 돌아왔다면 모델이 할 말을 다 하기 전에 상한에 걸린 것입니다. top-k는 모델마다 받는 자리가 달라 `inferenceConfig`가 아니라 모델별 추가 필드로 넘깁니다.

## 연습 문제

1. 보험사가 청구서 사진에서 청구 금액과 날짜를 글로 뽑으려 합니다. 다음 중 가장 먼저 확인할 기준은?\
   ① 모델이 이미지를 입력으로 받는가\
   ② 모델이 영상을 출력하는가\
   ③ 모델의 temperature 기본값\
   ④ 모델 이름의 길이

   답. ①. 입력 모달리티가 맞지 않으면 다른 기준은 볼 필요가 없습니다.
2. 다음 토큰 후보의 확률이 「A 0.4, B 0.3, C 0.2, D 0.1」입니다. top-p를 0.75로 두면 남는 후보는?\
   ① A\
   ② A, B\
   ③ A, B, C\
   ④ A, B, C, D

   답. ③. 확률을 높은 순서로 더하면 0.4, 0.7, 0.9이고, 0.75에 처음 닿는 것은 C까지입니다.
3. 계약서에서 당사자 이름과 계약 금액을 뽑는 기능이 같은 입력에도 매번 조금씩 다른 값을 냅니다. 가장 알맞은 조정은?\
   ① temperature를 낮춘다\
   ② temperature를 높인다\
   ③ 최대 토큰 수를 늘린다\
   ④ top-k를 크게 늘린다

   답. ①. temperature를 낮추면 가장 확률이 높은 후보로 쏠려 답이 일정해집니다. ②와 ④는 오히려 다양성을 키웁니다.
4. 시스템 프롬프트가 5,000토큰, 질문이 500토큰인 호출을 짧은 간격으로 100번 보냅니다. 캐시 읽기 단가를 정가의 10%로, 첫 호출은 정가로 셀 때 캐싱 없이 보낸 것과 캐싱한 것의 입력 토큰 분량은 각각?\
   ① 550,000과 104,500\
   ② 550,000과 55,000\
   ③ 500,000과 104,500\
   ④ 550,000과 5,500

   답. ①. 캐싱 없음은 $$5500 \times 100 = 550000$$ 입니다. 캐싱하면 첫 호출 5,500에 나머지 99번이 $$(5000 \times 0.1 + 500) = 1000$$ 씩이라 $$5500 + 99000 = 104500$$ 입니다.
5. 하루에 수백만 건의 짧은 리뷰를 긍정·부정으로 분류합니다. 모델 크기를 고르는 기준으로 가장 알맞은 것은?\
   ① 가장 큰 모델을 고른다\
   ② 요구 정확도를 채우는 가장 작은 모델부터 시험한다\
   ③ 컨텍스트 윈도우가 가장 긴 모델을 고른다\
   ④ 이미지 출력이 되는 모델을 고른다

   답. ②. 단순하고 호출이 많은 작업이라 큰 모델은 정확도 이득보다 비용과 지연이 더 커집니다.
6. 응답이 문장 중간에서 끊기고 `stopReason`이 `max_tokens`로 돌아옵니다. 원인과 대응은?\
   ① temperature가 너무 낮다 — 높인다\
   ② 최대 토큰 수가 응답 길이보다 작다 — 늘리거나 더 짧게 답하라고 지시한다\
   ③ top-p가 너무 크다 — 줄인다\
   ④ 캐시가 만료됐다 — 다시 저장한다

   답. ②. 상한에 걸려 끊긴 것이므로 상한을 늘리거나 응답 길이를 줄여야 합니다.
7. 사내 용어에 맞춰 파인튜닝한 모델이 꼭 필요한 프로젝트입니다. 모델 선택 단계에서 놓치면 가장 큰 손실이 나는 확인은?\
   ① 모델이 파인튜닝을 지원하는가\
   ② 모델의 기본 temperature\
   ③ 모델 카드의 글꼴\
   ④ 모델의 출시 연도

   답. ①. 커스터마이즈를 지원하지 않는 모델을 골랐다면 나중에 모델 선택부터 다시 해야 합니다.

일곱 문항 가운데 둘이 계산입니다. top-p는 높은 순서로 더해 가다 p에 처음 닿는 후보까지 남기고, 캐싱은 첫 호출과 나머지 호출을 갈라 더하면 됩니다. 나머지 다섯은 선택 기준과 추론 파라미터 가운데 무엇이 문제의 상황을 바꾸는 손잡이인지를 짚는 연습입니다.
