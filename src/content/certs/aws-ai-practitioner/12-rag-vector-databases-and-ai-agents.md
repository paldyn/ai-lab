시험 가이드 v1.1의 Task 3.1은 모델 선택과 추론 파라미터 다음에 RAG의 정의와 업무 적용, 벡터 임베딩을 저장하는 AWS 서비스, 그리고 AI 에이전트의 역할을 목표로 적었습니다. 셋은 한 줄로 이어집니다. RAG는 모델 밖에서 근거를 찾아 넣는 방식이고, 그 근거를 찾는 저장소가 벡터 데이터베이스이며, 에이전트는 검색을 여러 도구 가운데 하나로 쓰면서 실제 일까지 하는 애플리케이션입니다. 토큰·청크·임베딩은 앞의 편에서 이미 다뤘으므로 여기서는 그것들이 하나의 흐름으로 맞물리는 자리를 봅니다.

## RAG

### 정의

**RAG**(Retrieval Augmented Generation)는 모델이 답을 쓰기 전에 외부 데이터에서 질문과 관련된 내용을 찾아 프롬프트에 함께 넣어 주는 방식입니다. 이름의 세 낱말이 곧 순서입니다 — 찾고(검색), 프롬프트에 덧붙이고(증강), 그걸 읽고 답을 씁니다(생성). 모델의 파라미터는 하나도 바뀌지 않고, 바뀌는 것은 매번 모델에 들어가는 입력뿐입니다. 그래서 문서가 바뀌면 저장소만 갱신하면 되고, 답에 어느 문서를 근거로 썼는지 출처를 붙일 수 있습니다. 앞에서 본 환각을 줄이는 대표적인 방법이 이것입니다.

### 동작 순서

RAG는 미리 해 두는 준비 단계와 질문마다 도는 응답 단계로 갈립니다.

1. 문서를 모아 일정한 크기의 청크로 자른다
2. 청크마다 임베딩 모델로 벡터를 만든다
3. 벡터와 원문 청크를 벡터 저장소에 넣는다
4. 질문이 들어오면 같은 임베딩 모델로 질문을 벡터로 만든다
5. 저장소에서 질문 벡터와 가장 가까운 청크 몇 개를 찾는다
6. 찾은 청크를 질문과 함께 프롬프트에 넣는다
7. 모델이 그 프롬프트를 읽고 답을 쓴다

1~3이 준비, 4~7이 응답입니다. 질문과 문서에 같은 임베딩 모델을 써야 한다는 점이 놓치기 쉬운 자리입니다. 프롬프트에 실리는 분량도 여기서 정해져, 300토큰짜리 청크 다섯 개를 붙이면 질문 앞에 1,500토큰이 더해집니다.

### 파인튜닝 비교

| 기준 | RAG | 파인튜닝 |
| --- | --- | --- |
| 바뀌는 것 | 프롬프트에 들어가는 근거 | 모델의 파라미터 |
| 자주 바뀌는 정보 | 저장소만 갱신하면 됨 | 다시 학습해야 함 |
| 출처 표시 | 쉬움 | 어려움 |
| 맞는 자리 | 사내 규정·제품 정보 같은 사실 | 말투·형식·전문 용어 습관 |

「최신 정보」, 「출처를 함께 보여 달라」, 「문서가 매주 바뀐다」가 문항에 있으면 RAG 쪽이고, 「말투를 회사 문체에 맞춘다」면 파인튜닝 쪽입니다.

## Bedrock Knowledge Bases

### 관리형 RAG

**Amazon Bedrock Knowledge Bases**는 앞의 일곱 단계를 관리형으로 묶은 기능입니다. Amazon S3 같은 데이터 소스를 연결하고 임베딩 모델과 벡터 저장소를 고르면, 청크 자르기·임베딩·저장을 Knowledge Bases가 맡고 문서가 바뀌면 동기화로 다시 반영합니다. 검색만 해서 청크를 돌려받는 호출과, 검색부터 답 생성까지 한 번에 하는 호출 두 가지를 씁니다.

### 호출 코드

검색과 생성을 한 번에 하는 호출은 이렇습니다.

```python
import boto3

client = boto3.client("bedrock-agent-runtime", region_name="us-east-1")
resp = client.retrieve_and_generate(
    input={"text": "연차는 몇 시간 단위로 쪼개 쓸 수 있나요?"},
    retrieveAndGenerateConfiguration={
        "type": "KNOWLEDGE_BASE",
        "knowledgeBaseConfiguration": {
            "knowledgeBaseId": "KB12345678",  # 콘솔에서 만든 지식 기반의 ID
            "modelArn": "arn:aws:bedrock:us-east-1::foundation-model/amazon.nova-lite-v1:0",
        },
    },
)
print(resp["output"]["text"])
for c in resp["citations"]:
    for ref in c["retrievedReferences"]:
        print(ref["location"])
```

`citations`에 답의 근거가 된 청크와 그 위치가 돌아오므로, 화면에 출처를 함께 보여 줄 수 있습니다. 검색만 하려면 같은 클라이언트의 `retrieve`를 부르고 돌려받은 청크로 프롬프트를 직접 짭니다.

## 벡터 저장소

### Amazon OpenSearch Service

**벡터 데이터베이스**는 임베딩 벡터를 저장해 두고 주어진 벡터와 가까운 것을 빠르게 찾아 주는 저장소입니다. **Amazon OpenSearch Service**는 검색·분석 엔진으로, 키워드 검색과 벡터 검색을 함께 할 수 있습니다. 서버 관리가 없는 OpenSearch Serverless를 Knowledge Bases의 저장소로 고르면 콘솔이 컬렉션을 만들어 줘서 RAG를 처음 세울 때 손이 가장 덜 갑니다. 제품 번호처럼 정확히 일치해야 하는 낱말과 뜻이 비슷한 문장을 함께 찾아야 할 때 맞습니다.

### Aurora와 RDS for PostgreSQL

**Amazon Aurora PostgreSQL**과 **Amazon RDS for PostgreSQL**은 관계형 데이터베이스인데, pgvector 확장을 켜면 테이블의 한 열에 벡터를 담고 SQL로 유사도 검색을 할 수 있습니다. 이미 업무 데이터를 PostgreSQL에 두고 있다면 저장소를 새로 늘리지 않고 그 옆에 벡터를 둘 수 있다는 것이 이점입니다. 상품 표와 상품 설명 벡터를 한 쿼리로 함께 거를 수 있습니다.

### Neptune과 DocumentDB

**Amazon Neptune**은 그래프 데이터베이스로, 사람·제품·부서처럼 개체와 그 사이의 관계를 저장합니다. Neptune Analytics는 벡터 검색도 지원해, 비슷한 청크를 찾은 뒤 그 청크와 이어진 개체를 따라가며 근거를 넓히는 그래프 기반 RAG에 씁니다. **Amazon DocumentDB**는 JSON 문서를 저장하는 MongoDB 호환 데이터베이스이고, 벡터 검색을 지원해 문서 데이터 옆에 임베딩을 함께 둘 수 있습니다.

| 이미 가진 것이나 필요한 것 | 맞는 저장소 |
| --- | --- |
| 손 덜 가는 관리형 벡터 검색, 키워드와 함께 검색 | OpenSearch Service |
| 업무 데이터가 PostgreSQL에 있음 | Aurora PostgreSQL, RDS for PostgreSQL |
| 개체 사이의 관계를 따라가야 함 | Neptune |
| 데이터가 JSON 문서로 쌓여 있음 | DocumentDB |

## 업무 적용처

### 사내 문서 질의응답

RAG가 가장 먼저 쓰이는 자리는 사내 문서 질의응답입니다. 인사 규정·보안 지침·제품 매뉴얼처럼 양이 많고 자주 고쳐지는 문서를 저장소에 넣어 두면, 직원이 자연어로 묻고 근거 문서의 위치와 함께 답을 받습니다. 문서마다 부서별 접근 권한이 다르면, 검색할 때 메타데이터로 걸러 그 사람이 볼 수 있는 청크만 프롬프트에 넣어야 합니다. 모델이 안 본 문서는 답에 새어 나갈 수 없기 때문입니다.

### 고객 지원

고객 지원에서는 FAQ·정책·지난 상담 기록을 근거로 상담 챗봇이나 상담원 보조 화면이 답을 씁니다. 환불 정책이 바뀌어도 모델을 다시 학습시킬 필요 없이 문서만 바꾸면 다음 질문부터 새 정책이 반영됩니다. 다만 RAG는 조회해서 답할 뿐이어서, 「환불을 실제로 처리해 달라」는 요청은 다음 절의 에이전트가 맡을 자리입니다.

## AI 에이전트

### 역할

**AI 에이전트**는 목표를 받으면 스스로 할 일을 나누고, 도구를 불러 결과를 보고, 다음 할 일을 정하는 되풀이로 목표를 이루는 애플리케이션입니다. 멀티 에이전트 편에서 본 그 되풀이입니다. RAG와의 관계는 포함입니다 — 에이전트에게 Knowledge Bases 검색은 주문 조회 API나 메일 발송처럼 부를 수 있는 도구 가운데 하나입니다. RAG가 「무엇이 사실인가」에 답한다면, 에이전트는 그 사실을 바탕으로 「그래서 무엇을 할 것인가」까지 실행합니다. Amazon Bedrock Agents에 지식 기반과 액션 그룹을 함께 붙이면 이 모양이 됩니다.

### 업무 적용 사례

| 업무 | 에이전트가 하는 일 |
| --- | --- |
| 고객 환불 | 규정을 검색하고, 주문을 조회하고, 조건이 맞으면 환불 API를 부른 뒤 고객에게 알림 |
| IT 헬프데스크 | 장애 문의를 분류해 티켓을 만들고, 비밀번호 초기화 같은 정해진 조치를 실행 |
| 출장 예약 | 사내 출장 규정 안에서 항공과 숙소를 찾아 예약하고 일정을 캘린더에 넣음 |
| 영업 지원 | 새로 들어온 문의를 고객 관리 시스템에 기록하고 담당자를 배정 |

넷 모두 검색으로 끝나지 않고 다른 시스템에 무언가를 쓰거나 바꿉니다. 그래서 에이전트에는 RAG에는 없던 걱정이 붙습니다 — 어떤 도구를 어떤 권한으로 부를 수 있게 할지, 돈이 나가는 조치에 사람 승인을 끼울지를 설계 단계에서 정해야 합니다.

## 연습 문제

1. RAG의 응답 단계를 순서대로 배열하시오.\
   (가) 찾은 청크를 질문과 함께 프롬프트에 넣는다\
   (나) 질문을 임베딩 모델로 벡터로 만든다\
   (다) 모델이 프롬프트를 읽고 답을 쓴다\
   (라) 질문 벡터와 가까운 청크를 저장소에서 찾는다

   답. (나) → (라) → (가) → (다). 검색하고, 덧붙이고, 생성하는 차례입니다.
2. 사내 규정 문서 1,600개를 문서당 평균 25개 청크로 자르고, 청크마다 1,024차원 벡터를 만들어 차원당 4바이트로 저장합니다. 벡터만의 저장 용량은?\
   ① 약 40MB\
   ② 약 164MB\
   ③ 약 1.6GB\
   ④ 약 4MB

   답. ②. 청크는 $$1600 \times 25 = 40000$$ 개이고, 하나가 $$1024 \times 4 = 4096$$ 바이트라 $$40000 \times 4096 = 163840000$$ 바이트, 약 164MB입니다.
3. 회사가 업무 데이터를 이미 Amazon RDS for PostgreSQL에 두고 있고, 저장소를 새로 늘리지 않고 상품 설명의 임베딩을 같은 데이터베이스에서 검색하려 합니다. 알맞은 방법은?\
   ① pgvector 확장을 켜고 벡터 열을 추가한다\
   ② Amazon Neptune으로 데이터를 모두 옮긴다\
   ③ 모델을 파인튜닝해 상품 설명을 외우게 한다\
   ④ temperature를 낮춘다

   답. ①. RDS for PostgreSQL과 Aurora PostgreSQL은 pgvector로 벡터 검색을 할 수 있습니다.
4. Bedrock Knowledge Bases의 벡터 저장소로 고를 수 있는 AWS 서비스를 **둘** 고르시오.\
   ① Amazon OpenSearch Serverless\
   ② Amazon Aurora PostgreSQL\
   ③ AWS Transform\
   ④ Amazon Quick\
   ⑤ Kiro

   답. ①과 ②. 나머지 셋은 저장소가 아니라 각각 현대화 서비스, 업무용 작업 공간, 개발 환경입니다.
5. 제품 정보가 매주 바뀌고, 상담 챗봇의 답마다 근거 문서를 함께 보여 줘야 합니다. 가장 알맞은 접근은?\
   ① 매주 모델을 파인튜닝한다\
   ② RAG로 최신 문서를 검색해 근거와 함께 답한다\
   ③ 최대 토큰 수를 늘린다\
   ④ 모델 크기를 키운다

   답. ②. 저장소만 갱신하면 되고 근거의 출처를 붙일 수 있는 것이 RAG입니다.
6. 고객이 「지난주 주문을 취소하고 환불해 달라」고 합니다. 규정을 찾아 읽어 주는 데서 그치지 않고 주문 조회와 환불 처리까지 해야 합니다. 알맞은 구성은?\
   ① 지식 기반만 붙인 RAG 챗봇\
   ② 지식 기반과 주문·환불 API를 도구로 가진 AI 에이전트\
   ③ 이미지 생성 모델\
   ④ temperature가 높은 텍스트 모델

   답. ②. RAG는 조회해 답할 뿐이고, 다른 시스템에서 조치를 실행하는 것은 도구를 가진 에이전트입니다.
7. 사람·조직·프로젝트 사이의 관계를 따라가며 근거를 넓혀야 하는 질의응답입니다. 가장 알맞은 저장소는?\
   ① Amazon Neptune\
   ② Amazon DocumentDB\
   ③ Amazon S3 Glacier\
   ④ Amazon RDS for PostgreSQL

   답. ①. 개체와 관계를 저장하고 따라가는 것이 그래프 데이터베이스인 Neptune의 자리입니다.

일곱 문항이 가르는 것은 셋입니다. RAG의 일곱 단계 가운데 응답 단계의 차례, 이미 가진 데이터와 필요한 검색 방식으로 저장소를 고르는 기준, 그리고 답하는 RAG와 행동하는 에이전트의 선입니다. 저장 용량 계산은 청크 수에 벡터 하나의 바이트 수를 곱하면 됩니다.
