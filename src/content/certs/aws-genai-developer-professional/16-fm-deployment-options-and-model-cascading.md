앞 세 노트는 에이전트를 다뤘고, 이 노트부터 Task 2.2 「모델 배포 전략」입니다. 같은 모델이라도 어떻게 띄우느냐에 따라 비용의 모양, 지연, 한꺼번에 받을 수 있는 요청 수가 달라집니다. 4번 노트가 커스텀 모델을 배포하고 교체하는 수명주기를 봤다면, 여기서는 호출이 들어오는 길과 그 뒤에서 모델이 도는 그릇을 고르는 일을 봅니다.

## 호출 방식

### Lambda 온디맨드 호출

가장 가벼운 구성은 이벤트가 생길 때 Lambda가 Bedrock을 부르는 것입니다. S3에 문서가 올라오면 요약하고, 큐에 문의가 쌓이면 분류합니다. 이때 Bedrock은 **온디맨드** 방식으로 불립니다 — 미리 자원을 잡지 않고 쓴 입력·출력 토큰만큼 냅니다. 호출이 없으면 비용이 0이고 운영할 서버도 없습니다.

대가는 두 가지입니다. 온디맨드에는 계정·리전·모델별로 분당 요청 수와 토큰 수 할당량이 있어, 순간적으로 몰리면 제한 오류(`ThrottlingException`)가 납니다. 그리고 다른 고객과 같은 용량을 나눠 쓰므로 처리량이 보장되지 않습니다. 제한 오류는 지수 백오프 재시도와 교차 리전 추론으로 받아 내고, 그래도 모자라면 아래의 프로비저닝으로 갑니다.

### Bedrock 프로비저닝된 처리량

**프로비저닝된 처리량**(Provisioned Throughput)은 특정 모델의 처리 용량을 **모델 단위**(model unit)로 미리 사서 내 것으로 잡아 두는 방식입니다. 모델 단위 하나가 분당 처리할 수 있는 토큰 양이 모델마다 정해져 있고, 필요한 처리량을 그 값으로 나눠 단위 수를 정합니다. 약정 기간은 없음·1개월·6개월이고 길수록 단가가 내려갑니다.

```python
import boto3

bedrock = boto3.client("bedrock")
pt = bedrock.create_provisioned_model_throughput(
    provisionedModelName="support-summarizer",
    modelId="arn:aws:bedrock:ap-northeast-2:111122223333:custom-model/abc123",
    modelUnits=2,
    commitmentDuration="OneMonth",
)
arn = pt["provisionedModelArn"]  # 호출할 때 modelId 자리에 넣는다
```

용량을 잡아 둔 시간만큼 내므로 쓰지 않아도 비용이 나갑니다. 그래서 트래픽이 꾸준하고 많을 때, 처리량이 보장돼야 할 때, 그리고 Bedrock에서 파인튜닝한 커스텀 모델처럼 프로비저닝으로만 부를 수 있는 모델을 쓸 때 고릅니다.

## SageMaker AI 엔드포인트

### 엔드포인트의 종류

Bedrock에 없는 모델이나 직접 파인튜닝한 오픈 웨이트 모델은 SageMaker AI 엔드포인트에 띄웁니다. 엔드포인트는 요청을 받는 방식에 따라 넷으로 갈립니다.

| 종류 | 받는 방식 | LLM에서의 쓰임 |
| --- | --- | --- |
| 실시간 | 인스턴스가 늘 떠 있고 바로 응답 | 대화형 서비스. GPU 인스턴스를 고른다 |
| 서버리스 | 요청이 올 때 띄우고 쓴 만큼 냄 | GPU를 고를 수 없어 큰 LLM에는 맞지 않는다 |
| 비동기 | 요청을 큐에 넣고 결과를 S3에 씀 | 긴 문서 처리. 대기열이 비면 인스턴스를 0으로 줄일 수 있다 |
| 배치 변환 | 데이터셋 전체를 한 번에 처리 | 밤마다 도는 대량 요약 |

실시간 엔드포인트에는 **추론 구성 요소**(inference component)로 여러 모델을 한 엔드포인트에 나눠 올릴 수 있습니다. 모델마다 GPU 수와 메모리를 따로 잡아, 작은 모델 여럿이 큰 인스턴스 하나를 나눠 쓰게 합니다.

### 하이브리드 구성

**하이브리드 구성**은 요청의 성격에 따라 Bedrock과 SageMaker AI를 함께 쓰는 배치입니다. 범용 질의응답은 Bedrock 온디맨드로, 사내 용어로 파인튜닝한 분류 모델은 SageMaker 실시간 엔드포인트로, 밤 사이 대량 처리는 비동기 엔드포인트로 보냅니다. 앞단의 Lambda나 API Gateway가 요청을 보고 갈래를 정하므로, 사용자는 하나의 API만 봅니다. 3번 노트의 공급자 전환 구성과 합치면 한쪽 장애 때 다른 쪽으로 넘기는 길도 됩니다.

## 컨테이너 배포

### GPU 메모리 계산

LLM을 컨테이너로 띄울 때 먼저 따질 것은 가중치가 GPU 메모리에 들어가는가입니다. 가중치 메모리는 파라미터 수에 파라미터 하나의 바이트 수를 곱한 값이고, FP16이면 2바이트입니다. 70억(7B) 파라미터 모델은 $$7 \times 10^9 \times 2 = 14 \times 10^9$$ 바이트, 곧 약 14GB입니다. 130억(13B) 모델은 약 26GB라 24GB GPU 하나에 들어가지 않습니다. 이때 길은 둘입니다 — 가중치를 8비트로 양자화해 13GB로 줄이거나, 모델을 GPU 둘에 나눠 올리는 **텐서 병렬화**(tensor parallelism)를 씁니다.

가중치만 들어가서는 안 됩니다. 생성 중에는 앞 토큰들의 키·값을 저장하는 **KV 캐시**가 토큰마다 자랍니다. 토큰 하나의 KV 캐시는 키와 값 둘 × 층 수 × 은닉 차원 × 값 하나의 바이트 수이고, 층 32·은닉 4096·FP16인 모델이면 $$2 \times 32 \times 4096 \times 2 = 524288$$ 바이트, 약 0.5MB입니다. 4,096토큰짜리 요청 하나가 약 2GB를 쓰므로, 동시에 받을 요청 수는 가중치를 뺀 남은 메모리를 이 값으로 나눠 정해집니다.

### 토큰 처리 용량

GPU 사용률을 높이는 핵심은 요청을 묶어 한꺼번에 처리하는 배치입니다. LLM은 요청마다 출력 길이가 달라 고정 배치로 묶으면 짧은 요청이 긴 요청을 기다립니다. **연속 배치**(continuous batching, SageMaker LMI 문서의 rolling batch)는 토큰 한 단계마다 끝난 요청을 빼고 새 요청을 넣어 GPU가 놀지 않게 합니다. SageMaker의 LMI(Large Model Inference) 컨테이너는 vLLM·TensorRT-LLM 같은 엔진을 이 방식으로 돌리며, 설정은 환경 변수로 줍니다.

```python
env = {
    "HF_MODEL_ID": "s3://my-bucket/models/support-13b/",
    "OPTION_TENSOR_PARALLEL_DEGREE": "2",   # GPU 둘에 나눠 올린다
    "OPTION_ROLLING_BATCH": "vllm",
    "OPTION_MAX_ROLLING_BATCH_SIZE": "32",  # 동시에 처리할 요청 수
    "OPTION_MAX_MODEL_LEN": "4096",
}
```

동시 요청 수를 늘리면 처리량(초당 토큰)은 오르지만 요청 하나의 지연도 늘고 KV 캐시 메모리가 커집니다. 부하 시험으로 지연 목표를 지키는 가장 큰 값을 찾고, 자동 확장의 기준 지표도 GPU 사용률이나 동시 요청 수로 둡니다.

## 모델 로딩 전략

### 전통 ML과의 차이

전통 ML 모델은 수 MB에서 수백 MB라 컨테이너가 뜨면서 몇 초 안에 메모리에 올라옵니다. LLM은 수십 GB의 가중치를 S3에서 받아 GPU에 올려야 해서 새 인스턴스가 요청을 받기까지 수 분이 걸릴 수 있습니다. 이 차이가 배포와 확장 모두에 영향을 줍니다 — 자동 확장으로 인스턴스를 늘려도 로딩이 끝날 때까지는 용량이 늘지 않고, 기본 상태 확인 시간 안에 로딩을 못 끝내면 배포가 실패합니다.

### 로딩 시간 줄이기

그래서 LLM 엔드포인트에는 로딩을 위한 설정을 따로 둡니다.

1. 프로덕션 변형에 `ModelDataDownloadTimeoutInSeconds`와 `ContainerStartupHealthCheckTimeoutInSeconds`를 길게 잡아 큰 가중치를 받고 올릴 시간을 준다.
2. 가중치를 tar.gz로 묶지 않고 압축 없는 S3 접두사로 두어, 받은 뒤 푸는 시간을 없앤다.
3. 가중치를 미리 GPU 수에 맞게 나눠 저장해 두거나 가중치를 흘려 받으며 올리는 SageMaker의 빠른 모델 로더를 써서 시작 시간을 줄인다.
4. 확장 정책은 로딩 시간만큼 앞서 움직이게, 기준을 낮게 잡거나 예약 확장을 더한다.

가중치를 줄이는 양자화도 로딩 시간을 같이 줄입니다. 14GB가 7GB가 되면 받아 올리는 양이 절반입니다.

## 모델 캐스케이딩

### 소형 사전학습 모델

모든 요청에 가장 큰 모델을 쓸 필요는 없습니다. 감성 분류, 개체 추출, 짧은 답변 분류 같은 특정 작업은 작은 사전학습 모델이 충분히 해내고, 지연과 비용이 몇 분의 일입니다. 특정 작업용 소형 모델은 SageMaker JumpStart에서 고르거나 Bedrock의 작은 모델을 쓰고, 그 작업의 평가 세트로 큰 모델과의 정확도 차이를 먼저 잽니다.

### API 기반 캐스케이딩

**모델 캐스케이딩**은 요청을 먼저 작은 모델에 보내고, 결과가 믿을 만하지 않을 때만 큰 모델로 넘기는 배치입니다. 넘길지 말지는 작은 모델이 낸 확신 점수, 출력 형식 검증의 통과 여부, 또는 판정 프롬프트가 정합니다. 각 모델을 API로 부르므로 Lambda 하나가 「작은 모델 호출 → 기준 검사 → 필요하면 큰 모델 호출」을 차례로 하면 됩니다.

비용 효과는 넘기는 비율이 정합니다. 요청 하나의 비용이 작은 모델 1, 큰 모델 10이고 20%를 넘긴다면, 모든 요청이 작은 모델을 거치므로 평균은 $$1 + 0.2 \times 10 = 3$$ 입니다. 처음부터 큰 모델만 쓴 10에 비해 70%가 줄어듭니다. 넘기는 비율이 90%라면 $$1 + 0.9 \times 10 = 10$$ 으로 이득이 사라지므로, 작은 모델이 대부분을 받아 낼 수 있는 작업에만 씁니다. 같은 계열 두 모델 사이에서 이 판정을 관리형으로 해 주는 것이 Bedrock 지능형 프롬프트 라우팅입니다. 시험 가이드는 Task 2.2에 Lambda 온디맨드 호출, Bedrock 프로비저닝된 처리량, SageMaker AI 하이브리드 구성, 컨테이너 배포 패턴, LLM 모델 로딩 전략, 소형 모델과 API 기반 캐스케이딩을 적고 있어, 트래픽의 모양과 모델의 크기를 주고 배포 방식이나 비용을 고르게 하는 꼴로 물을 수 있습니다.

## 연습 문제

1. 하루 내내 초당 요청이 일정하게 많고 처리량이 보장돼야 하는 요약 서비스가 Bedrock 온디맨드에서 제한 오류를 자주 받습니다. 알맞은 조치는?\
   ① Lambda 메모리를 늘린다\
   ② 해당 모델에 프로비저닝된 처리량을 사서 그 ARN으로 호출한다\
   ③ SageMaker 서버리스 추론으로 옮긴다\
   ④ 요청마다 온도를 낮춘다

   답. ②. 꾸준한 고부하에 처리량 보장이 필요하면 용량을 잡아 두는 프로비저닝이 맞습니다. ③은 GPU를 고를 수 없어 LLM에 맞지 않고 ①·④는 할당량과 무관합니다.
2. 130억 파라미터 모델을 FP16으로 띄우려 합니다. 가중치에 필요한 메모리는 약 몇 GB이며, GPU당 24GB인 인스턴스에서 텐서 병렬 차수를 최소 얼마로 잡아야 하는가?

   답. $$13 \times 10^9 \times 2 = 26 \times 10^9$$ 바이트로 약 26GB입니다. GPU 하나(24GB)에 안 들어가므로 최소 2로 나눠 GPU당 13GB를 올립니다. KV 캐시 몫까지 생각하면 남는 메모리가 GPU당 약 11GB입니다.
3. 층 40, 은닉 차원 5120, FP16인 모델에서 토큰 하나의 KV 캐시는 몇 바이트이며, 2,048토큰 요청 하나는 약 몇 GB를 쓰는가?

   답. $$2 \times 40 \times 5120 \times 2 = 819200$$ 바이트(약 0.78MB)이고, $$819200 \times 2048 = 1677721600$$ 바이트로 약 1.68GB(1.56GiB)입니다.
4. 다음 가운데 LLM 엔드포인트의 시작 시간을 줄이는 방법을 **둘** 고르시오.\
   ① 가중치를 압축 없는 S3 접두사에 두어 푸는 단계를 없앤다\
   ② 엔드포인트를 서버리스 추론으로 바꾼다\
   ③ 가중치를 8비트로 양자화해 받아 올릴 양을 줄인다\
   ④ 상태 확인 시간 제한을 짧게 줄인다

   답. ①과 ③. ②는 GPU를 못 쓰고, ④는 로딩을 못 마친 컨테이너를 실패로 만들어 배포가 깨집니다 — 늘려야 할 값입니다.
5. 작은 모델 요청 비용이 2, 큰 모델이 12입니다. 모든 요청을 작은 모델에 먼저 보내고 30%를 큰 모델로 넘길 때 평균 비용은? 큰 모델만 쓸 때보다 몇 % 싼가?

   답. $$2 + 0.3 \times 12 = 5.6$$ 입니다. 큰 모델만 쓰면 12이므로 $$(12 - 5.6) / 12 \approx 0.533$$ , 약 53% 쌉니다.
6. 범용 질의응답과 사내 데이터로 파인튜닝한 오픈 웨이트 분류 모델을 한 API 뒤에서 함께 제공하려 합니다. 하이브리드 구성은?

   답. 범용 질의응답은 Bedrock 온디맨드로 부르고, 파인튜닝한 분류 모델은 GPU 인스턴스의 SageMaker AI 실시간 엔드포인트에 띄웁니다. API Gateway 뒤의 Lambda가 요청 종류를 보고 두 갈래 중 하나로 보냅니다.
