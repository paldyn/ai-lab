도메인 1이 FM을 고르고 데이터를 대 주는 일이었다면, 도메인 2 「Implementation and Integration」은 그 FM을 실제 시스템에 엮는 일입니다. 시험 가이드에서 비중은 26%이고, 첫 태스크인 Task 2.1이 에이전트형 AI입니다. 이 노트는 그중 에이전트를 어떻게 짜고 여럿을 어떻게 조율하는지를 다룹니다. 추론 루프와 안전장치는 다음 노트, 도구와 MCP 서버의 구현은 그다음 노트의 몫입니다.

## 에이전트의 구성

### 모델·도구·루프

**에이전트**는 FM이 목표를 받아 스스로 다음 행동을 고르고, 도구를 불러 결과를 보고, 다시 다음 행동을 고르는 루프를 도는 시스템입니다. 세 부품이 서로 얹혀 있습니다. 모델은 무엇을 할지 정하는 판단 장치이고, 도구는 모델이 직접 못 하는 일(주문 조회, 계산, 사내 API 호출)을 대신하는 함수이며, 루프는 모델의 판단을 도구 호출로 옮기고 그 결과를 다시 모델에 넣어 주는 실행 틀입니다. 모델이 「이제 답할 수 있다」고 판단하면 루프가 끝납니다.

단일 FM 호출과 가르는 기준은 다음 단계를 누가 정하느냐입니다. 개발자가 단계를 미리 다 정해 두면 그건 워크플로이고, 모델이 실행 중에 단계를 고르면 에이전트입니다. 정해진 절차를 확실히 밟아야 하는 업무에는 워크플로가, 질문마다 필요한 도구가 달라지는 업무에는 에이전트가 맞습니다.

### 메모리와 상태

FM은 호출 사이에 아무것도 기억하지 않으므로, 에이전트가 「자율적으로」 일을 이어 가려면 기억을 바깥에 두어야 합니다. 이때 갈라 둘 것이 셋입니다.

| 무엇 | 담는 것 | 사는 기간 | 두는 곳의 예 |
| --- | --- | --- | --- |
| 대화 이력 | 주고받은 메시지 | 한 세션 | 에이전트 메모리, DynamoDB |
| 에이전트 상태 | 루프가 쓰는 키·값(현재 주문 번호, 시도 횟수) | 한 세션 | 세션 관리자가 S3 등에 저장 |
| 장기 메모리 | 사용자 선호, 지난 세션 요약 | 세션을 넘어 | AgentCore Memory, 벡터 저장소 |

**상태**는 모델에게 보여 주는 대화와 달리 코드가 읽고 쓰는 값이라는 점이 다릅니다. 시도 횟수를 대화 문장으로 남겨 두면 모델이 그것을 세어야 하지만, 상태에 두면 코드가 확실히 셉니다. 대화가 길어지면 오래된 메시지를 잘라 내거나 요약해 토큰 예산을 지킵니다.

## Strands Agents

### Agent와 @tool

**Strands Agents**는 AWS가 공개한 오픈소스 에이전트 SDK입니다. 모델과 도구와 시스템 프롬프트만 주면 루프는 SDK가 돕니다. 도구는 파이썬 함수에 `@tool` 데코레이터를 붙여 만들고, 함수의 독스트링과 타입 힌트가 모델에게 보이는 도구 설명이 됩니다.

```python
from strands import Agent, tool
from strands.models import BedrockModel

@tool
def order_status(order_id: str) -> str:
    """주문 번호로 배송 상태를 조회한다."""
    return lookup(order_id)  # 사내 조회 함수

agent = Agent(
    model=BedrockModel(model_id="anthropic.claude-sonnet-4-20250514-v1:0"),
    tools=[order_status],
    system_prompt="고객 주문 문의에 답하는 상담원이다.",
)
agent("A-1024 주문 어디쯤 왔어요?")
```

모델은 Bedrock이 기본이고 다른 공급자로 바꿀 수 있습니다. 대화 이력은 에이전트 객체가 들고 있으며, 세션 관리자를 붙이면 S3나 파일에 저장해 다음 요청에서 이어 갑니다.

### 에이전트를 도구로

Strands에서 여러 에이전트를 엮는 가장 단순한 길은 에이전트를 도구로 쓰는 것입니다. 환불 전문 에이전트와 배송 전문 에이전트를 각각 만들고, 그 둘을 `@tool` 함수로 감싸 상위 에이전트의 도구 목록에 넣습니다. 상위 에이전트는 질문을 보고 어느 전문가를 부를지 정하고, 전문가의 답을 모아 최종 답을 씁니다. 이 밖에 에이전트들이 서로 일을 넘기는 스웜(swarm)과, 노드와 간선으로 순서를 못 박는 그래프 구성도 SDK가 제공합니다.

### MCP 도구

**MCP**(Model Context Protocol)는 에이전트와 도구 사이의 표준 규약입니다. 도구를 MCP 서버로 한 번 만들어 두면 Strands든 다른 프레임워크든 같은 방식으로 목록을 받아 호출합니다. Strands는 MCP 클라이언트를 내장하고 있어, 서버에 연결한 뒤 받은 도구 목록을 그대로 에이전트에 넘깁니다.

```python
from mcp import stdio_client, StdioServerParameters
from strands.tools.mcp import MCPClient

docs = MCPClient(lambda: stdio_client(
    StdioServerParameters(command="uvx", args=["awslabs.aws-documentation-mcp-server@latest"])
))
with docs:
    agent = Agent(tools=docs.list_tools_sync())
    agent("S3 수명주기 규칙 설명해 줘")
```

도구 쪽 코드를 에이전트마다 따로 붙이지 않고 한곳에서 관리한다는 것이 MCP의 이득입니다. 서버를 Lambda와 ECS로 어떻게 세우는지는 15번 노트에서 다룹니다.

## AWS Agent Squad

### 분류기와 라우팅

**AWS Agent Squad**(예전 이름 Multi-Agent Orchestrator)는 여러 에이전트를 앞에서 받아 주는 오픈소스 조율 프레임워크입니다. 중심은 **분류기**(classifier)로, 사용자 입력과 대화 이력을 보고 등록된 에이전트 가운데 가장 알맞은 하나를 고릅니다. 고른 에이전트가 답하고, 대화는 에이전트별로 저장되어 다음 차례에 이어집니다.

```python
from agent_squad.orchestrator import AgentSquad
from agent_squad.agents import BedrockLLMAgent, BedrockLLMAgentOptions

squad = AgentSquad()
squad.add_agent(BedrockLLMAgent(BedrockLLMAgentOptions(
    name="Billing", description="요금·환불·청구서 문의")))
squad.add_agent(BedrockLLMAgent(BedrockLLMAgentOptions(
    name="Shipping", description="배송 조회·주소 변경")))

response = await squad.route_request("환불 언제 들어와요?", "user-7", "session-42")
```

분류기가 보는 것은 각 에이전트의 `description`입니다. 설명이 겹치면 라우팅이 흔들리므로 에이전트마다 맡는 범위를 서로 안 겹치게 적습니다.

### Strands와의 분담

두 도구는 층이 다릅니다. Strands Agents는 에이전트 하나를 만드는 SDK이고, Agent Squad는 이미 있는 에이전트 여럿 앞에 서서 요청을 나눠 주는 층입니다. 그래서 함께 쓸 수 있습니다 — 전문 에이전트 각각은 Strands나 Bedrock Agents로 만들고 그 앞에 Agent Squad를 세웁니다.

| 질문 | Strands Agents | AWS Agent Squad |
| --- | --- | --- |
| 무엇을 하나 | 모델·도구·루프로 에이전트를 만든다 | 입력을 분류해 알맞은 에이전트로 보낸다 |
| 다음 행동을 고르는 것 | 에이전트의 모델 | 분류기(한 차례에 하나를 고른다) |
| 알맞은 요구 | 도구를 여러 번 부르며 문제를 푸는 에이전트 | 영역이 갈린 상담 창구를 하나로 묶기 |

Agent Squad에도 감독 에이전트가 하위 에이전트 여럿에 일을 나눠 맡기는 구성이 있어, 한 차례에 여러 전문가의 답이 필요하면 그쪽을 씁니다.

## 모델 분담과 조율

### 특화 FM과 앙상블

모든 하위 작업을 가장 큰 모델 하나에 맡길 필요는 없습니다. 의도 분류는 작고 빠른 모델이, 긴 계약서 검토는 큰 모델이, 이미지 설명은 멀티모달 모델이 맡게 나누는 것이 **특화 FM 분담**입니다. 같은 질문을 여러 모델에 던져 결과를 합치는 **모델 앙상블**에서는 합치는 규칙, 곧 사용자 지정 집계 로직을 코드로 적습니다. 분류 결과면 다수결을, 점수면 가중 평균을, 요약이면 판정 모델이 가장 근거에 충실한 것을 고르게 합니다.

가중 평균의 예를 들면, 세 모델이 어떤 리뷰의 긍정 확률을 0.9·0.6·0.7로 냈고 검증 세트 성능에 따라 가중치를 0.5·0.2·0.3으로 줬다면 $$0.5 \times 0.9 + 0.2 \times 0.6 + 0.3 \times 0.7 = 0.78$$ 입니다. 다수결이었다면 셋 다 0.5를 넘어 긍정이고, 가중 평균도 기준 0.5를 넘으니 결론이 같습니다. 둘이 갈리는 것은 표가 2 대 1로 나뉘고 소수 쪽 가중치가 클 때입니다.

### 모델 선택 프레임워크

**모델 선택 프레임워크**는 요청마다 어느 모델로 보낼지를 정하는 규칙의 묶음입니다. 기준은 작업 종류, 입력 길이, 필요한 정확도, 지연 예산, 비용이고, 이 규칙을 코드에 박지 않고 설정으로 빼 두면 모델을 바꿀 때 배포 없이 바꿉니다 — 3번 노트의 AppConfig 구성과 같은 생각입니다. Bedrock의 지능형 프롬프트 라우팅은 같은 계열의 두 모델 사이에서 질문마다 응답 품질을 예측해 고르는 관리형 기능이라, 직접 규칙을 짜기 전의 첫 선택지가 됩니다.

### Step Functions와 프롬프트 체이닝

**프롬프트 체이닝**은 큰 작업을 여러 프롬프트로 쪼개 앞 프롬프트의 출력을 다음 프롬프트의 입력으로 넘기는 방식입니다. Bedrock 문서는 이것을 Step Functions로 짜는 길을 안내합니다. Step Functions에는 Bedrock 모델 호출 통합이 있어 Task 상태 하나가 Lambda 없이 바로 모델을 부릅니다.

1. Task 상태가 문서를 요약하는 프롬프트로 모델을 부른다.
2. Parallel 상태가 요약을 받아 위험 조항 추출과 번역을 동시에 돌린다.
3. Choice 상태가 위험 조항이 있으면 검토 대기로, 없으면 바로 보고서 생성으로 보낸다.
4. 마지막 Task 상태가 결과를 합쳐 보고서를 쓴다.

Strands 에이전트와 이 흐름은 서로 대신하지 않습니다. 단계가 정해진 부분은 Step Functions가 재시도·분기·기록까지 맡고, 그 가운데 한 단계만 에이전트로 두면 됩니다. 시험 가이드는 Task 2.1에 Strands Agents·AWS Agent Squad·MCP와 Step Functions 에이전트 설계 패턴·Bedrock 프롬프트 체이닝을 함께 적고 있어, 요구 사항이 「에이전트 하나를 만들기」인지 「여러 에이전트로 나눠 보내기」인지 「정해진 단계를 확실히 밟기」인지 가려 도구를 고르는 꼴로 물을 수 있습니다.

## 연습 문제

1. 고객 창구에 요금·배송·기술 지원 에이전트가 이미 따로 있습니다. 사용자 질문 하나를 받아 알맞은 에이전트 하나로 보내는 앞단을 가장 적은 코드로 세우려면?\
   ① Strands 에이전트 하나에 세 영역의 도구를 전부 넣는다\
   ② AWS Agent Squad에 세 에이전트를 등록하고 분류기가 고르게 한다\
   ③ Step Functions Map 상태로 세 에이전트를 모두 부른다\
   ④ 세 에이전트의 답을 다수결로 합친다

   답. ②. 이미 있는 에이전트 앞에서 입력을 분류해 나눠 주는 것이 Agent Squad의 일입니다. ①은 에이전트를 다시 만드는 것이고, ③과 ④는 하나만 필요한데 셋을 다 부릅니다.
2. 에이전트가 도구를 세 번까지만 다시 시도하게 하려 합니다. 시도 횟수를 대화 이력과 에이전트 상태 가운데 어디에 두어야 하며 그 이유는?

   답. 에이전트 상태. 상태는 코드가 읽고 쓰는 키·값이라 횟수를 확실히 세고 비교할 수 있습니다. 대화 이력에 문장으로 남기면 모델이 세어야 해서 틀릴 수 있습니다.
3. 세 모델이 같은 문의의 「긴급」 확률을 0.4·0.8·0.3으로 냈고 가중치는 0.2·0.5·0.3입니다. 가중 평균과, 기준 0.5에서의 판정은?

   답. $$0.2 \times 0.4 + 0.5 \times 0.8 + 0.3 \times 0.3 = 0.08 + 0.40 + 0.09 = 0.57$$ 이므로 긴급입니다. 다수결로는 0.5를 넘는 것이 하나뿐이라 긴급이 아니어서, 가중치가 큰 모델이 결론을 바꾼 경우입니다.
4. 다음 중 Strands Agents에 대한 설명으로 옳은 것을 **둘** 고르시오.\
   ① `@tool`을 붙인 함수의 독스트링이 모델에게 보이는 도구 설명이 된다\
   ② MCP 서버의 도구를 쓰려면 도구마다 래퍼 함수를 손으로 써야 한다\
   ③ 다른 에이전트를 도구로 감싸 상위 에이전트에 넘길 수 있다\
   ④ 입력을 분류해 에이전트 하나를 고르는 분류기가 핵심 구성 요소다

   답. ①과 ③. ②는 틀렸습니다 — 내장 MCP 클라이언트가 받은 도구 목록을 그대로 넘깁니다. ④는 Agent Squad의 설명입니다.
5. 계약서를 요약하고, 요약에서 위험 조항을 뽑고, 위험 조항이 있을 때만 법무 검토로 보내는 처리를 재시도와 실행 기록까지 남기며 돌리려 합니다. 알맞은 구성은?

   답. Step Functions로 프롬프트를 체이닝합니다. Task 상태가 Bedrock을 바로 불러 요약과 추출을 차례로 하고, Choice 상태가 위험 조항 여부로 갈라 검토 단계로 보냅니다. 단계가 정해져 있으므로 에이전트보다 워크플로가 맞습니다.
6. 의도 분류는 작은 모델이, 긴 문서 분석은 큰 모델이 맡게 하되, 모델 배정을 바꿀 때 배포를 다시 하지 않으려 합니다. 어떻게 짜는가?

   답. 작업 종류·입력 길이·지연 예산으로 모델을 고르는 모델 선택 규칙을 코드 밖 설정(예: AppConfig)에 두고, 호출 코드는 그 설정을 읽어 모델 ID를 정합니다.
