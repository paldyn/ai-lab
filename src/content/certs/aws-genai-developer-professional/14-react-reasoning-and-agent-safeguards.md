앞 노트는 에이전트를 짜고 여럿을 엮는 일이었습니다. 에이전트는 다음 행동을 스스로 고르기 때문에, 잘못 고르면 같은 도구를 끝없이 부르거나 건드리면 안 되는 자원에 손을 대거나 아무도 확인하지 않은 결정을 내보냅니다. 이 노트는 Task 2.1 가운데 에이전트가 어떻게 생각하고, 언제 멈추고, 어디까지 손댈 수 있으며, 언제 사람에게 넘기는지를 다룹니다.

## ReAct 루프

### 추론과 행동

**ReAct**는 Reasoning과 Acting을 합친 이름으로, 모델이 생각(무엇을 해야 하는가)을 적고, 행동(도구 호출)을 하고, 관찰(도구가 돌려준 결과)을 받아 다시 생각하는 순환입니다. 생각 단계가 앞 노트들에서 다룬 **chain-of-thought**, 곧 답에 이르는 중간 단계를 글로 풀어 쓰게 하는 지시와 같은 것이고, ReAct는 그 중간 단계 사이사이에 도구 호출을 끼워 넣은 것입니다.

```text
생각: 환불 가능 여부를 알려면 구매일이 필요하다.
행동: get_order(order_id="A-1024")
관찰: {"purchased": "2026-11-10", "item": "이어폰"}
생각: 오늘이 11-25이니 15일 지났다. 규정은 30일 이내다.
답: 환불 가능합니다.
```

생각을 적게 하면 도구를 왜 불렀는지가 기록에 남아, 잘못된 답이 나왔을 때 어느 생각에서 어긋났는지 짚을 수 있습니다.

### Step Functions로 짜는 루프

ReAct 루프를 Step Functions 상태로 펼치면 각 차례가 실행 기록에 한 줄씩 남습니다.

1. Task 상태가 지금까지의 대화와 관찰을 넣어 모델을 부른다.
2. Choice 상태가 응답을 본다 — 도구 호출 요청이면 3으로, 최종 답이면 끝으로.
3. Task 상태가 요청된 도구의 Lambda를 부른다.
4. Pass 상태가 관찰을 대화에 붙이고 차례 수를 하나 올린 뒤 1로 돌아간다.

같은 루프를 Strands 같은 SDK 안에서 돌릴 수도 있습니다. Step Functions로 펼쳤을 때 얻는 것은 차례마다의 입출력 기록, 상태별 재시도와 오류 처리, 그리고 아래에서 다룰 중단 조건과 사람 승인 단계를 상태 하나로 끼울 수 있다는 점입니다.

## 중단 조건과 타임아웃

### 중단 조건

**중단 조건**(stopping conditions)은 모델이 「다 했다」고 말하지 않아도 루프를 끝내는 규칙입니다. 모델은 같은 도구를 같은 인자로 거듭 부르며 빙빙 돌 수 있으므로, 끝을 모델의 판단에만 맡기면 비용과 시간이 한없이 늘어납니다. 위 루프에서는 Choice 상태에 조건을 더합니다.

- 차례 수가 상한(예: 8)에 닿으면 끝낸다.
- 같은 도구를 같은 인자로 두 번 연속 부르면 끝낸다.
- 쓴 토큰 합이 예산을 넘으면 끝낸다.

끝낼 때는 그냥 멈추지 않고 「답을 찾지 못했다」는 응답과 함께 상담원 연결 같은 다음 길로 보냅니다. 상태 머신 전체에는 `TimeoutSeconds`를 걸어 실행 시간의 상한도 둡니다.

### Lambda 타임아웃

도구를 맡은 Lambda 함수에도 따로 상한이 있습니다. Lambda 함수의 타임아웃은 최대 900초(15분)이고 기본값은 3초입니다. 느린 외부 API를 부르는 도구라면 함수 타임아웃을 그 API의 예상 응답 시간보다 조금 길게 잡고, 함수를 부르는 Task 상태에도 `TimeoutSeconds`를 둡니다. 두 값의 관계가 중요합니다 — Task 상태의 타임아웃이 함수보다 짧으면 함수는 계속 도는데 워크플로만 실패로 넘어갑니다.

```json
"CallTool": {
  "Type": "Task",
  "Resource": "arn:aws:states:::lambda:invoke",
  "TimeoutSeconds": 60,
  "Retry": [{
    "ErrorEquals": ["Lambda.TooManyRequestsException"],
    "IntervalSeconds": 2, "MaxAttempts": 3, "BackoffRate": 2.0
  }],
  "Catch": [{ "ErrorEquals": ["States.ALL"], "Next": "ToolFailed" }],
  "Next": "AppendObservation"
}
```

위 재시도는 첫 시도가 실패한 뒤 2초, 4초, 8초를 기다리며 세 번 더 시도합니다. 기다리는 시간 합은 $$2 + 4 + 8 = 14$$ 초입니다. 그래도 실패하면 `Catch`가 받아 도구 실패를 관찰로 돌려주는 상태로 보내고, 모델은 다른 길을 고를 수 있습니다.

## 자원 경계와 서킷 브레이커

### IAM 자원 경계

에이전트가 어떤 도구를 고를지는 모델이 정하지만, 그 도구가 무엇에 손댈 수 있는지는 IAM이 정합니다. 프롬프트에 「삭제하지 마라」고 적는 것은 부탁일 뿐이고, 실행 역할에 삭제 권한이 없어야 막힙니다. 도구 Lambda마다 실행 역할을 따로 주고 그 도구가 쓰는 자원과 행동만 허용합니다.

```json
{
  "Effect": "Allow",
  "Action": ["dynamodb:GetItem", "dynamodb:Query"],
  "Resource": "arn:aws:dynamodb:ap-northeast-2:111122223333:table/Orders"
}
```

주문 조회 도구에는 읽기만 주고, 쓰기가 필요한 환불 도구는 별도 역할에 둡니다. 개발자가 만드는 역할 전체에 상한을 씌우려면 **권한 경계**(permissions boundary)를 붙입니다 — 역할의 정책이 무엇을 허용하든 경계 밖의 권한은 효력이 없습니다.

### 서킷 브레이커

**서킷 브레이커**는 실패가 이어지는 대상을 한동안 아예 부르지 않게 끊는 패턴입니다. 3번 노트에서 FM 공급자 장애에 쓴 것과 같은 구조를 도구에도 씁니다. 상태는 셋입니다.

| 상태 | 동작 | 넘어가는 조건 |
| --- | --- | --- |
| 닫힘 | 정상적으로 호출한다 | 실패가 기준(예: 1분에 5번)을 넘으면 열림으로 |
| 열림 | 호출하지 않고 곧바로 대체 응답을 낸다 | 정해진 시간(예: 30초)이 지나면 반열림으로 |
| 반열림 | 시험 삼아 한 번만 호출한다 | 성공하면 닫힘으로, 실패하면 다시 열림으로 |

Step Functions에서는 도구별 상태와 실패 횟수를 DynamoDB 항목에 두고, 도구를 부르기 전 Choice 상태가 그 값을 읽어 열림이면 호출을 건너뜁니다. 재시도는 한 번의 일시적 실패를 넘기는 장치이고 서킷 브레이커는 지속되는 장애로 번지는 것을 막는 장치라, 둘을 함께 씁니다. 에이전트가 고장 난 도구를 수십 번 거듭 부르며 비용과 시간을 태우는 것이 서킷 브레이커가 막는 실패입니다.

## 사람이 끼는 자리

### 검토·승인 프로세스

돈이 나가거나 되돌릴 수 없는 행동 앞에는 사람의 승인을 둡니다. Step Functions에서는 Task 상태의 리소스 ARN 뒤에 `.waitForTaskToken`을 붙여 흐름을 멈추고, 상태가 내준 작업 토큰을 검토자에게 보냅니다. 검토자가 승인하거나 거절하면 그 토큰으로 `SendTaskSuccess`나 `SendTaskFailure`를 불러 흐름을 잇습니다. 표준 워크플로는 한 실행이 최대 1년까지 이어질 수 있어 사람의 검토를 며칠 기다려도 됩니다. 검토 대기에도 `HeartbeatSeconds`나 `TimeoutSeconds`를 두어 아무도 응답하지 않으면 정해진 기본 경로로 넘깁니다.

### API Gateway 피드백 수집

승인과 별개로, 에이전트의 답이 맞았는지를 사용자에게 묻는 창구가 있어야 개선이 이어집니다. API Gateway에 피드백 엔드포인트를 열고 응답 ID와 좋아요·싫어요, 고친 답을 받아 Lambda가 DynamoDB나 S3에 쌓습니다. 이렇게 모인 피드백은 프롬프트 템플릿을 고치거나 평가 세트를 늘리는 재료가 됩니다. 검토자의 승인 화면도 같은 API를 통해 토큰을 되돌려 보내게 짜면, 승인과 피드백이 한 창구로 들어옵니다.

### 사람 보강 패턴

**사람 보강**(human augmentation)은 에이전트가 사람을 대신하는 대신 사람의 일을 거드는 배치입니다. 에이전트가 초안·근거·추천을 만들고 사람이 최종 결정을 내립니다. 어디까지 자동으로 두고 어디서 사람에게 넘길지는 행동의 위험으로 가릅니다.

| 행동 | 배치 |
| --- | --- |
| 조회·요약처럼 되돌릴 필요가 없는 것 | 에이전트가 끝까지 처리 |
| 일정 금액 이하 환불 | 에이전트가 처리하고 사후 검토 |
| 기준 금액 초과 환불, 계약 변경 | 에이전트가 초안을 내고 사람이 승인 |

모델의 확신 점수가 낮을 때도 사람에게 넘기는 갈래를 둡니다. 시험 가이드는 Task 2.1에 ReAct·중단 조건·Lambda 타임아웃·IAM 경계·서킷 브레이커와 Step Functions 검토·승인, API Gateway 피드백, 사람 보강 패턴을 함께 적고 있어, 「에이전트가 멈추지 않는다」·「권한 밖 자원에 손댄다」·「장애 난 도구를 거듭 부른다」·「사람 확인이 필요하다」 같은 증상을 받아 맞는 장치를 고르는 꼴로 물을 수 있습니다.

## 연습 문제

1. ReAct 에이전트가 같은 검색 도구를 같은 검색어로 계속 부르며 끝나지 않습니다. 가장 알맞은 조치는?\
   ① 모델의 온도를 높인다\
   ② 차례 수 상한과 같은 호출 반복을 잡는 중단 조건을 Choice 상태에 둔다\
   ③ 도구 Lambda의 메모리를 늘린다\
   ④ 검색 도구의 IAM 권한을 넓힌다

   답. ②. 루프의 끝을 모델에만 맡기지 않는 중단 조건이 필요합니다. ①은 반복을 막는 보장이 없고 ③·④는 반복과 무관합니다.
2. Step Functions Task 상태에 `IntervalSeconds` 3, `MaxAttempts` 3, `BackoffRate` 2.0인 재시도를 걸었습니다. 재시도 사이에 기다리는 시간의 합은?

   답. 21초. 3초, 6초, 12초를 기다리므로 $$3 + 6 + 12 = 21$$ 입니다.
3. 도구 Lambda의 타임아웃은 120초인데 그 함수를 부르는 Task 상태의 `TimeoutSeconds`가 30초입니다. 응답에 50초 걸리는 호출에서 무슨 일이 생기는가?

   답. 30초에 Task 상태가 `States.Timeout`으로 실패하지만 Lambda 함수는 50초까지 계속 돌아 작업을 끝냅니다. 워크플로는 실패로 처리했는데 부수 효과는 일어난 상태가 되므로, 두 값을 맞추고 도구를 멱등하게 만듭니다.
4. 다음 가운데 서킷 브레이커가 「열림」일 때의 동작으로 옳은 것을 **둘** 고르시오.\
   ① 대상을 호출하지 않고 곧바로 대체 응답을 낸다\
   ② 실패할 때마다 대기 시간을 두 배로 늘리며 재시도한다\
   ③ 정해진 시간이 지나면 시험 호출을 허용하는 반열림으로 넘어간다\
   ④ IAM 권한을 거둬 대상을 막는다\
   ⑤ 요청을 사람 검토 대기열에 쌓는다

   답. ①과 ③. ②는 재시도의 지수 백오프이고, ④는 서킷 브레이커가 아니라 권한 설계이며, ⑤는 사람 승인 단계입니다.
5. 주문 조회 에이전트가 프롬프트 주입으로 주문 테이블의 항목을 지우려 했습니다. 프롬프트를 고치는 것 말고 실제로 막는 방법은?

   답. 조회 도구 Lambda의 실행 역할에 `dynamodb:GetItem`·`dynamodb:Query`만 허용하고 삭제 행동을 주지 않습니다. 역할 전체에 권한 경계를 씌우면 실수로 넓은 정책을 붙여도 경계 밖 권한은 효력이 없습니다.
6. 50만 원이 넘는 환불은 담당자 승인을 받은 뒤에만 실행하되, 담당자가 이틀 안에 응답하지 않으면 거절로 처리하려 합니다. Step Functions 구성은?

   답. 금액을 Choice 상태로 가르고, 초과 쪽에 `.waitForTaskToken` Task 상태를 둬 작업 토큰을 담당자에게 보냅니다. 승인하면 `SendTaskSuccess`로 환불 단계로, 거절하면 `SendTaskFailure`로 갑니다. 그 상태에 `TimeoutSeconds` 172800(이틀)을 걸고 타임아웃을 `Catch`로 받아 거절 경로로 보냅니다.
