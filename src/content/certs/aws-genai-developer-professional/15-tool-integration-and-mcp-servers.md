앞 두 노트는 에이전트가 도구를 고르고 부르는 쪽을 봤습니다. 이 노트는 반대편, 곧 불려 가는 도구를 어떻게 만드는지를 다룹니다. 도구의 이름과 인자를 어떻게 적어야 모델이 바르게 부르는지, 모델이 잘못된 인자를 넣었을 때 도구가 어떻게 받아 내는지, 여러 에이전트가 같이 쓰는 도구를 MCP 서버로 어디에 세우는지가 Task 2.1의 나머지 skill입니다.

## 함수 정의

### 표준화된 함수 정의

모델은 도구의 코드를 보지 못하고 **함수 정의**만 봅니다. 함수 정의는 도구의 이름, 언제 쓰는지에 대한 설명, 그리고 인자의 이름·타입·필수 여부를 적은 입력 스키마로 이루어지고, 입력 스키마는 JSON Schema로 적습니다. Bedrock Converse API에서는 이것을 `toolSpec`으로 넘깁니다.

```python
tool_config = {"tools": [{"toolSpec": {
    "name": "get_refund_policy",
    "description": "상품 분류별 환불 가능 기간과 조건을 조회한다. 환불 문의에만 쓴다.",
    "inputSchema": {"json": {
        "type": "object",
        "properties": {
            "category": {"type": "string", "enum": ["전자", "의류", "식품"]},
            "days_since_purchase": {"type": "integer", "minimum": 0},
        },
        "required": ["category"],
    }},
}}]}

resp = bedrock.converse(modelId=MODEL_ID, messages=msgs, toolConfig=tool_config)
```

정의를 **표준화**한다는 것은 팀의 모든 도구가 같은 규칙으로 이름과 설명과 스키마를 적는다는 뜻입니다. 동사로 시작하는 이름, 「언제 쓰고 언제 쓰지 않는지」를 적은 설명, 고를 값이 정해져 있으면 `enum`, 값의 범위가 있으면 `minimum` 같은 제약을 둡니다. 스키마가 좁을수록 모델이 엉뚱한 값을 넣을 여지가 줄어듭니다.

### 도구 호출의 왕복

모델이 도구를 쓰기로 하면 응답의 `stopReason`이 `tool_use`가 되고, 내용에 `toolUse` 블록(도구 이름, 호출 ID, 인자)이 담겨 옵니다. 실제로 함수를 실행하는 것은 모델이 아니라 애플리케이션입니다. 애플리케이션이 함수를 돌린 뒤 같은 호출 ID를 단 `toolResult` 블록을 사용자 메시지로 붙여 다시 `converse`를 부르면, 모델이 그 결과를 읽고 답을 이어 씁니다. 결과가 오류라면 `toolResult`에 `status`를 `error`로 두어 모델이 실패를 알게 합니다.

## Lambda 도구

### 파라미터 검증

스키마를 좁혀도 모델이 스키마에 맞지 않는 인자를 낼 수 있습니다. 그래서 도구를 맡은 Lambda가 들어온 인자를 다시 검사합니다. 모델의 출력은 사용자 입력과 마찬가지로 믿을 수 없는 입력이기 때문입니다. 같은 JSON Schema로 검증하면 정의와 검사가 한 벌이 됩니다.

```python
import jsonschema

def handler(event, context):
    args = event["input"]
    try:
        jsonschema.validate(args, SCHEMA)
    except jsonschema.ValidationError as e:
        return {"status": "error",
                "message": f"인자 오류: {e.message}. category는 전자·의류·식품 중 하나다."}
    return {"status": "success", "policy": find_policy(args["category"])}
```

### 오류 처리

도구가 실패했을 때 예외를 그대로 던지면 루프가 통째로 멈춥니다. 대신 모델이 읽고 다음 행동을 고칠 수 있는 오류를 돌려줍니다. 위 코드처럼 무엇이 틀렸고 어떤 값이 허용되는지를 문장으로 적어 주면, 모델이 인자를 고쳐 다시 부릅니다. 오류는 성격에 따라 다르게 다룹니다.

| 오류 | 예 | 도구의 처리 |
| --- | --- | --- |
| 인자 오류 | 없는 분류 값 | 허용 값을 적어 모델에 돌려준다 |
| 일시 오류 | 하류 API 제한 초과 | Lambda 안에서 백오프 재시도, 그래도 실패하면 오류로 돌려준다 |
| 영구 오류 | 대상 주문이 없음 | 재시도하지 않고 사실을 그대로 돌려준다 |

도구가 부수 효과(환불 실행)를 가진다면 같은 요청 ID로 두 번 불려도 한 번만 실행되게 **멱등성**을 갖춥니다. 재시도와 모델의 반복 호출이 겹치면 같은 환불이 두 번 나갈 수 있기 때문입니다.

## Strands API의 사용자 지정

### 도구와 모델 공급자

13번 노트에서 본 `@tool` 데코레이터가 가장 흔한 사용자 지정입니다. Strands는 데코레이터가 붙은 함수의 시그니처와 독스트링에서 위의 함수 정의를 자동으로 만들어 주므로, 손으로 `toolSpec`을 쓰지 않아도 표준 형식이 지켜집니다. 독스트링의 인자 설명도 스키마의 설명으로 들어갑니다.

```python
from strands import Agent, tool

@tool
def get_refund_policy(category: str, days_since_purchase: int = 0) -> dict:
    """상품 분류별 환불 가능 기간과 조건을 조회한다.

    Args:
        category: 전자, 의류, 식품 중 하나
        days_since_purchase: 구매 후 지난 날 수
    """
    return find_policy(category, days_since_purchase)
```

모델도 바꿀 수 있습니다. 기본은 Bedrock이지만 SDK의 모델 공급자 인터페이스를 따라 다른 엔드포인트를 붙이면, 에이전트 코드는 그대로 두고 판단 장치만 갈아 끼웁니다.

### 훅과 대화 관리

도구를 부르기 전후, 모델을 부르기 전후 같은 지점에 코드를 끼우는 **훅**(hooks)도 Strands API가 제공하는 사용자 지정입니다. 도구 호출 전에 인자를 기록하거나, 특정 도구는 사람 승인 없이 못 부르게 막거나, 호출 횟수를 세어 상한을 거는 일을 에이전트 루프를 고치지 않고 붙입니다. 대화 이력을 얼마나 남길지는 대화 관리자가 정합니다 — 최근 메시지 몇 개만 남기는 슬라이딩 창이 기본이고, 오래된 부분을 요약으로 바꾸는 관리자로 바꿀 수 있습니다. 14번 노트의 중단 조건과 권한 경계를 에이전트 안쪽에서 거는 자리가 이 훅입니다.

## MCP 서버

### 무상태 Lambda 서버

MCP 서버는 도구 목록을 알려 주는 `tools/list`와 도구를 실행하는 `tools/call`을 JSON-RPC 메시지로 받습니다. 원격 서버는 HTTP로 이 메시지를 주고받는데, 요청마다 필요한 것이 요청 안에 다 들어 있는 **무상태**(stateless) 모드로 돌리면 서버가 세션을 기억하지 않아도 됩니다. 무상태 서버는 요청 하나에 함수 실행 하나가 대응하는 Lambda와 잘 맞습니다 — 호출이 없으면 비용이 없고, 몰리면 저절로 늘어납니다.

```python
from mcp.server.fastmcp import FastMCP

mcp = FastMCP("refund-tools", stateless_http=True)

@mcp.tool()
def get_refund_policy(category: str) -> str:
    """상품 분류별 환불 가능 기간을 조회한다."""
    return find_policy(category)
```

이 서버를 Lambda 뒤에 두고 API Gateway나 함수 URL로 HTTP 끝점을 열면, 여러 에이전트가 같은 주소로 붙습니다. 인증은 끝점 앞의 IAM 인증이나 권한 부여자로 겁니다.

### ECS 서버

모든 도구가 Lambda에 맞지는 않습니다. 실행이 15분을 넘거나, 수 GB의 모델이나 색인을 메모리에 올려 둬야 하거나, 데이터베이스 연결을 오래 쥐고 있어야 하거나, 세션마다 상태를 유지해야 하는 도구는 **Amazon ECS**에 컨테이너로 띄운 MCP 서버가 맡습니다. 컨테이너는 늘 떠 있어 콜드 스타트가 없고 메모리·CPU를 크게 잡을 수 있으며, 로드 밸런서 뒤에서 작업 수를 조절해 규모를 맞춥니다.

| 질문 | Lambda MCP 서버 | ECS MCP 서버 |
| --- | --- | --- |
| 실행 시간 | 최대 15분 | 제한 없음 |
| 상태 | 무상태가 전제 | 세션 상태·연결 유지 가능 |
| 메모리 | 최대 10,240MB | 작업 정의로 크게 잡는다 |
| 비용 모양 | 호출한 만큼 | 떠 있는 시간만큼 |
| 맞는 도구 | 짧은 조회·계산·API 중계 | 긴 처리, 큰 색인, 브라우저 자동화 |

### MCP 클라이언트 라이브러리

에이전트마다 도구 호출 코드를 따로 쓰면 인증·재시도·오류 해석이 제각각이 됩니다. **MCP 클라이언트 라이브러리**는 서버에 연결하고 도구 목록을 받고 도구를 부르는 일을 한 방식으로 감싸, 서버가 Lambda든 ECS든 에이전트 쪽 코드가 같게 합니다. Strands의 `MCPClient`가 그런 라이브러리이고, MCP 공식 SDK의 클라이언트를 써도 됩니다. 팀 안에서 이 클라이언트를 공용 모듈로 두고 인증 헤더와 타임아웃을 거기서 정하면, 일관된 접근 패턴이 코드로 강제됩니다. 시험 가이드는 Task 2.1에 Strands API의 사용자 지정 동작, 표준화된 함수 정의, Lambda 오류 처리와 파라미터 검증, Lambda 무상태 MCP 서버, ECS MCP 서버, MCP 클라이언트 라이브러리를 나란히 적고 있어, 도구의 실행 시간·상태·메모리 요구를 보고 서버를 세울 곳을 고르는 꼴로 물을 수 있습니다.

## 연습 문제

1. 모델이 환불 도구에 `category`로 「가전」을 넣어 계속 실패합니다. 허용 값은 전자·의류·식품입니다. 함수 정의와 도구 양쪽에서 할 일은?

   답. 함수 정의의 스키마에 `"enum": ["전자", "의류", "식품"]`을 두어 고를 값을 좁히고, 도구 Lambda는 같은 스키마로 다시 검증해 「category는 전자·의류·식품 중 하나다」처럼 허용 값을 적은 오류를 돌려줍니다. 모델은 그 오류를 읽고 인자를 고쳐 다시 부릅니다.
2. Bedrock Converse 응답의 `stopReason`이 `tool_use`입니다. 다음에 애플리케이션이 할 일로 옳은 것은?\
   ① 모델이 도구를 이미 실행했으므로 응답을 사용자에게 보여 준다\
   ② `toolUse` 블록의 이름과 인자로 함수를 실행하고, 같은 호출 ID의 `toolResult`를 붙여 다시 호출한다\
   ③ 같은 요청을 온도를 낮춰 다시 보낸다\
   ④ 함수 정의를 지우고 다시 호출한다

   답. ②. 도구를 실행하는 것은 애플리케이션이고, 결과를 호출 ID와 함께 돌려줘야 모델이 답을 잇습니다.
3. 다음 도구 가운데 ECS에 띄운 MCP 서버가 Lambda보다 알맞은 것을 **둘** 고르시오.\
   ① 환율 API를 한 번 불러 값을 돌려주는 도구\
   ② 3GB 벡터 색인을 메모리에 올려 두고 검색하는 도구\
   ③ 두 수의 할인율을 계산하는 도구\
   ④ 한 번 돌면 20분 걸리는 문서 일괄 변환 도구

   답. ②와 ④. ②는 큰 색인을 늘 메모리에 두어야 하고, ④는 Lambda 최대 실행 시간 15분을 넘습니다. ①과 ③은 짧은 무상태 작업이라 Lambda가 맞습니다.
4. 환불 도구가 하류 결제 API의 지연으로 재시도되면서 같은 환불이 두 번 실행됐습니다. 도구 쪽에서 막는 방법은?

   답. 요청 ID(예: 대화 ID와 호출 ID를 합친 값)를 멱등 키로 받아, 이미 처리한 키면 실행하지 않고 지난 결과를 돌려줍니다. 처리한 키는 DynamoDB 조건부 쓰기로 기록해 동시 호출에서도 한 번만 성공하게 합니다.
5. Lambda MCP 서버의 평균 실행이 0.4초이고 하루 호출이 25,000건입니다. 하루 실행 시간의 합은 몇 초이며, 같은 일을 하루 종일 떠 있는 컨테이너 한 대로 할 때의 가동 시간과 비교하면?

   답. $$25000 \times 0.4 = 10000$$ 초, 약 2.8시간입니다. 컨테이너는 하루 86,400초 떠 있으므로 실제 일하는 시간은 그 $$10000 / 86400 \approx 11.6$$ %입니다. 짧고 띄엄띄엄한 호출이라 호출한 만큼 내는 Lambda가 비용 모양에 맞습니다(단가는 메모리 설정과 요금표로 따로 계산합니다).
6. 에이전트 다섯 팀이 각자 MCP 서버 호출 코드를 써서 인증 방식과 타임아웃이 제각각입니다. 접근 방식을 맞추는 방법은?

   답. MCP 클라이언트 라이브러리를 공용 모듈로 감싸 인증 헤더·타임아웃·재시도를 한곳에서 정하고, 모든 에이전트가 그 모듈로만 서버에 붙게 합니다.
