[앞 노트](/learn/certs/adsp/08-bigdata-analysis-methodology)에서 빅데이터 분석 방법론 다섯 단계를 짚었습니다. 그 첫 단계인 분석 기획은 「무엇을 분석할 것인가」가 정해져 있어야 시작되는데, 그 무엇을 찾아내는 일이 이번 노트의 **분석 과제 발굴**입니다. 과제를 찾는 길은 둘입니다. 풀어야 할 문제가 이미 보이면 위에서 아래로 내려가는 하향식 접근을, 문제가 무엇인지조차 흐리면 데이터에서 위로 올라가는 상향식 접근을 씁니다. 두 길로 건진 과제는 하나의 정의서로 모이고, 그 정의서가 프로젝트 관리의 출발점이 됩니다. 이 노트는 그 순서대로 갑니다.

## 하향식 접근

### 네 단계

**하향식 접근**(Top-down Approach)은 문제가 주어진 상태에서 해법을 찾아 내려가는 방식입니다. [분석 주제 네 유형](/learn/certs/adsp/06-analysis-planning-and-four-topic-types)으로 말하면 분석 대상을 아는 칸, 곧 최적화와 솔루션 쪽에 어울립니다. 단계는 넷이고 순서가 정해져 있습니다.

| 단계 | 영문 | 하는 일 |
| --- | --- | --- |
| 문제 탐색 | Problem Discovery | 풀 수 있는지는 따지지 않고 문제 후보를 빠짐없이 모은다 |
| 문제 정의 | Problem Definition | 비즈니스 문제를 데이터 분석 문제로 바꿔 적는다 |
| 해결방안 탐색 | Solution Search | 어떤 기법과 역량으로 풀지 갈래를 고른다 |
| 타당성 검토 | Feasibility Study | 경제성과 데이터·기술 면에서 해볼 만한지 따진다 |

문제 탐색 단계에서 해결 가능성을 따지지 않는 데는 이유가 있습니다. 처음부터 「이건 데이터가 없어서 안 된다」고 걸러 내면 정작 중요한 문제가 목록에 오르지도 못합니다. 걸러 내는 일은 마지막 타당성 검토가 맡습니다.

### 비즈니스 모델 캔버스

문제를 빠짐없이 모으려면 회사를 몇 조각으로 나눠 조각마다 훑는 틀이 있어야 합니다. 그 틀이 **비즈니스 모델 캔버스**이고, 분석 기획에서는 다섯 블록으로 씁니다.

| 블록 | 무엇을 보나 | 분석 과제의 예 |
| --- | --- | --- |
| 업무(Operation) | 제품·서비스를 만들고 전달하는 내부 활동 | 생산 공정 불량 원인 분석 |
| 제품(Product) | 만들어 내는 제품과 서비스 자체 | 제품 사용 로그로 기능 개선점 찾기 |
| 고객(Customer) | 제품을 쓰는 사람과 전달 채널 | 이탈 가능성이 높은 고객 찾기 |
| 규제와 감사(Regulation & Audit) | 법규와 내부 감사 요구 | 이상 거래 탐지 |
| 지원 인프라(IT & Human Resource) | 시스템과 인력 | 시스템 장애 예측, 인력 배치 최적화 |

앞의 셋은 가치를 만드는 흐름(업무·제품·고객)이고 뒤의 둘은 그 흐름을 받치는 쪽입니다. 다섯 이름을 그대로 대 놓고 하나를 다른 말로 바꿔 끼운 선택지 — 예를 들어 「재무」나 「경쟁사」 — 를 가려낼 수 있어야 합니다.

### 분석 기회 확장

캔버스는 회사 안을 훑는 틀이라 바깥 변화를 놓치기 쉽습니다. 그래서 범위를 넓혀 보는 관점 넷을 덧붙입니다. 거시적 관점은 사회·기술·경제·환경·정치(STEEP) 다섯 영역의 흐름을 봅니다. 경쟁자 확대 관점은 지금의 경쟁사뿐 아니라 대체재와 신규 진입자까지 봅니다. 시장의 니즈 변화 관점은 고객과 채널, 그리고 고객의 선택에 영향을 주는 영향자를 봅니다. 역량의 재해석 관점은 우리 회사의 내부 역량과 파트너 네트워크를 다시 보며 새로 할 수 있는 일을 찾습니다.

### 외부 참조 모델

세 번째 길은 남이 이미 한 분석을 빌려 오는 것입니다. 동종·유사 업계의 사례를 벤치마킹한 목록이 **외부 참조 모델**이고, 이를 쓰면 처음부터 생각해 내는 것보다 빠르게 후보를 얻습니다. 건진 후보는 **분석 유스케이스**로 적어 둡니다. 유스케이스는 그 분석을 어떤 업무에 어떻게 쓰고 어떤 효과를 기대하는지를 적은 한 단위의 쓰임새이고, 이것이 있어야 뒤 단계에서 착수할지 말지를 따질 근거가 생깁니다.

## 문제 정의와 해결방안

### 문제 정의

문제 탐색에서 모은 것은 아직 비즈니스의 말로 적혀 있습니다. 문제 정의 단계는 그것을 데이터로 풀 수 있는 말로 옮깁니다. 「고객 이탈이 늘었다」는 비즈니스 문제이고, 「고객의 이용 기록으로 다음 달 이탈 여부를 예측한다」가 데이터 분석 문제입니다. 바꿀 때는 필요한 데이터와 기법이 무엇인지까지 함께 적어야 다음 단계에서 해법을 고를 수 있습니다. 이 변환의 주인은 분석가만이 아니라 현업입니다 — 최종 사용자의 관점에서 무엇을 바라는지가 문제 정의의 기준이 됩니다.

### 해결방안 탐색

해결방안은 두 물음으로 갈립니다. 우리에게 그 분석 역량이 있는가, 그리고 기존 시스템으로 풀 수 있는가입니다.

| | 기존 시스템으로 가능 | 새 시스템이 필요 |
| --- | --- | --- |
| 분석 역량 있음 | 기존 시스템 개선 활용 | 시스템 고도화 |
| 분석 역량 없음 | 교육·채용으로 역량 확보 | 전문 업체 소싱 |

역량도 시스템도 없을 때가 외부 전문 업체에 맡기는 칸입니다. 표의 칸 이름과 두 축의 조합을 엇갈려 놓은 선택지를 가려야 합니다.

### 타당성 검토

마지막 단계는 해볼 만한지를 따집니다. 경제적 타당성은 드는 비용과 얻는 효과를 견주는 것이고, 데이터 및 기술적 타당성은 필요한 데이터가 있는지, 분석 역량과 시스템이 받쳐 주는지를 봅니다. 여러 대안을 이 둘로 평가해 하나를 고르고, 고른 대안이 분석 과제 정의서로 넘어갑니다.

## 상향식 접근

### 디자인 사고

**상향식 접근**(Bottom-up Approach)은 문제가 정해지지 않은 상태에서 데이터를 먼저 보고 거기서 문제를 끌어올리는 방식입니다. 하향식이 「왜(Why) 이런 일이 생기는가」에서 출발한다면, 상향식은 사물을 있는 그대로 보며 「무엇(What)이 보이는가」에서 출발합니다. 이 태도를 체계로 만든 것이 **디자인 사고**(Design Thinking)인데, 생각을 넓게 펼치는 발산(Diverge)과 그중에서 쓸 것을 좁히는 수렴(Converge)을 번갈아 밟습니다. 상향식이 주로 기대는 것은 발산 쪽이고, 하향식은 수렴 쪽에 가깝습니다. 두 방식은 서로 배척하지 않아서 실제로는 섞어 씁니다.

### 비지도 학습

데이터에서 문제를 끌어올리려면 정답이 정해져 있지 않은 상태에서 패턴을 찾는 기법이 필요합니다. 정답 칸(목표 변수)이 없는 데이터에서 구조를 찾는 것이 **비지도 학습**이고, 장바구니에 함께 담기는 상품을 찾는 연관 규칙이나 비슷한 고객끼리 묶는 군집 분석이 그 예입니다. 반대로 정답이 붙은 데이터로 예측 모형을 만드는 지도 학습은 목표가 정해져 있으므로 하향식과 어울립니다. 「상향식 — 비지도 학습」, 「하향식 — 지도 학습」의 짝을 바꿔 놓은 선택지를 조심합니다.

## 프로토타이핑 접근법

### 네 걸음

상향식의 대표적인 진행 방식이 **프로토타이핑 접근법**입니다. 완성된 요구사항을 기다리지 않고 먼저 간단한 분석을 만들어 보여 주고, 그 반응을 보며 고쳐 나가는 시행착오 방식입니다. 한 바퀴는 네 걸음입니다.

1. 가설 생성
2. 디자인에 대한 실험
3. 실제 환경에서의 테스트
4. 테스트 결과에서 통찰 도출 및 가설 확인

네 번째 걸음에서 가설이 틀렸으면 첫 걸음으로 돌아가 새 가설을 세우므로, 이 순환이 문제를 점점 또렷하게 만듭니다.

### 필요한 상황

프로토타이핑이 필요한 자리는 세 가지 불확실성으로 정리됩니다. 문제에 대한 인식 수준이 낮아 무엇을 풀지 말로 못 할 때, 필요한 데이터가 실제로 있는지 확신할 수 없을 때, 데이터를 쓰는 목적이 도중에 바뀔 수 있을 때입니다. 셋 다 「처음부터 다 정하고 시작할 수 없다」는 공통점이 있고, 이것이 [KDD와 CRISP-DM 노트](/learn/certs/adsp/07-kdd-and-crisp-dm)에서 본 폭포수 모델과 갈리는 지점입니다. 사용자도 자기가 원하는 것을 처음부터 알지 못하는 경우가 많아서, 만들어 보인 결과가 오히려 요구사항을 끌어냅니다.

## 분석 과제 정의서

### 담는 항목

하향식이든 상향식이든 건진 과제는 **분석 과제 정의서**로 옮겨 적습니다. 다양한 방식으로 도출한 과제를 같은 양식에 담아 비교하고 관리하려는 문서입니다. 들어가는 항목은 필요한 소스 데이터, 분석 방법, 데이터 입수 난이도, 분석 수행 주기, 분석 결과에 대한 검증 오너십, 상세 분석 과정 등입니다. 데이터를 어디서 얼마나 쉽게 얻는지, 얼마나 자주 돌리는지, 결과를 누가 책임지고 확인하는지가 적히므로 이 문서가 곧 프로젝트 계획의 입력물이 됩니다.

### 두 접근의 비교

| | 하향식 | 상향식 |
| --- | --- | --- |
| 출발점 | 주어진 문제 | 데이터 |
| 질문 | 왜(Why) | 무엇(What) |
| 어울리는 기법 | 지도 학습 | 비지도 학습 |
| 진행 방식 | 4단계 순서대로 | 프로토타이핑 순환 |
| 디자인 사고 | 수렴 | 발산 |

## 분석 프로젝트 관리

### 5대 주요 특성

분석 프로젝트도 일정·범위·품질을 관리하는 점은 다른 프로젝트와 같지만, 데이터와 모형에서 오는 특성이 다섯 더 얹힙니다. 이것이 **분석 프로젝트 5대 주요 특성**입니다.

| 특성 | 관리할 것 |
| --- | --- |
| Data Size | 다루는 데이터의 양 |
| Data Complexity | 정형·비정형이 섞이고 출처가 여럿인 정도 |
| Speed | 실시간인지 일괄 처리인지, 결과가 나와야 하는 속도 |
| Analytic Complexity | 모형의 정확도와 해석 가능성 사이의 균형 |
| Accuracy & Precision | 실제와의 거리와 반복했을 때의 흔들림 |

Analytic Complexity는 복잡한 모형일수록 정확도는 오르지만 왜 그런 결과가 나왔는지 설명하기 어려워지는 문제입니다. 해석이 필요한 업무라면 복잡도를 일부러 낮춥니다.

### 정확도와 정밀도

마지막 특성의 두 낱말이 갈리는 자리입니다. **정확도**(Accuracy)는 모형의 값이 실제 값에 얼마나 가까운가이고 활용 측면에서 중요합니다. **정밀도**(Precision)는 모형을 반복해 돌렸을 때 결과가 얼마나 일정한가이고 안정성 측면에서 중요합니다. 과녁으로 말하면 화살이 한가운데 모이는 것이 정확도, 어디든 한곳에 촘촘히 모이는 것이 정밀도입니다. 둘은 서로 당기는 관계(트레이드오프)여서 한쪽을 올리면 다른 쪽이 떨어지는 경우가 많습니다. 활용과 안정성의 짝을 뒤바꾼 선택지가 오답입니다.

### 관리 지식 영역

분석 프로젝트도 일반 프로젝트 관리 지식체계(KS A ISO 21500)의 주제 그룹을 따릅니다. 통합, 이해관계자, 범위, 자원, 시간, 원가, 리스크, 품질, 조달, 의사소통 열 영역입니다. 분석 프로젝트에서 특히 눈여겨볼 것은 조달입니다 — 외부 데이터 구매나 분석 도구 도입, 앞의 해결방안 탐색에서 고른 전문 업체 소싱이 여기에 들어갑니다. 범위도 분석을 진행하며 자주 바뀌므로 프로토타이핑으로 진행할 때는 범위 변경을 미리 계획에 넣어 둡니다.

   ① 기존 시스템 개선 활용\

   ③ 교육·채용으로 역량 확보\

   답. ④. 역량이 있으면 고도화, 시스템이 있으면 교육·채용으로 역량을 확보합니다.
